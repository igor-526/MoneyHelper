# frontend-workspaces Specification

## Purpose
Текущее рабочее пространство (воркспейс) пользователя на frontend: `WorkspaceContext`/`useCurrentWorkspaceId` —
синхронный доступ к `workspace_id` для всех data-хуков приложения; `RequireWorkspace` — маршрутная защита ниже
`RequireAuth`, определяющая, какой воркспейс текущий (или что его нужно выбрать/создать); сохранение выбора в
`localStorage`; управление воркспейсами (список, создание, переименование, удаление, переключение) в разделе
«Настройки». Backend — уже готовый `workspaces` (020).

## Requirements
### Requirement: Текущий воркспейс — React Context, а не серверное состояние
`features/workspaces` SHALL предоставлять `WorkspaceContext` (React Context, хранит только `workspace_id: string`)
и хук `useCurrentWorkspaceId()`, читающий этот контекст. Вызов `useCurrentWorkspaceId()` вне
`WorkspaceContext.Provider` MUST бросать исключение с понятным сообщением (тот же приём, что `useApiClient` вне
`ApiClientProvider`), а не молча возвращать `undefined`. Любой компонент или hook, которому нужен текущий
`workspace_id` для построения пути запроса или ключа кэша, SHALL получать его через `useCurrentWorkspaceId()`, а не
через пропы, проброшенные вручную через дерево компонентов.

#### Scenario: Хук вне провайдера бросает исключение
- **WHEN** `useCurrentWorkspaceId()` вызывается в дереве компонентов без `WorkspaceContext.Provider` выше
- **THEN** вызов бросает исключение с сообщением, что хук нужно вызывать внутри провайдера воркспейса

#### Scenario: Хук внутри провайдера возвращает текущий id
- **WHEN** `useCurrentWorkspaceId()` вызывается внутри `WorkspaceContext.Provider value={id}`
- **THEN** хук возвращает `id`

### Requirement: `RequireWorkspace` — маршрутная защита ниже `RequireAuth`
Защищённые маршруты приложения SHALL быть обёрнуты компонентом `RequireWorkspace` внутри уже существующего
`RequireAuth` (между `RequireAuth` и `AppLayout`). Пока список воркспейсов пользователя загружается,
`RequireWorkspace` SHALL показывать тот же индикатор полноэкранной загрузки, что и `RequireAuth` во время проверки
сессии. После загрузки списка `RequireWorkspace` SHALL определить состояние:
- список воркспейсов пуст — отображается пустое состояние с формой создания первого воркспейса, без перехода на
  отдельный маршрут;
- список содержит ровно один воркспейс, а сохранённый в `localStorage` `workspace_id` отсутствует или не входит в
  список — этот единственный воркспейс становится текущим автоматически, без отображения списка выбора (выбирать
  не из чего) и без записи в `localStorage` для этого случая — значение выводится заново при каждой загрузке, пока
  воркспейс остаётся единственным;
- список содержит два и более воркспейса, а сохранённый `workspace_id` отсутствует или не входит в список
  (устаревший или удалённый воркспейс) — отображается список существующих воркспейсов для выбора, без перехода на
  отдельный маршрут;
- сохранённый `workspace_id` входит в список — `RequireWorkspace` оборачивает `children` в
  `WorkspaceContext.Provider value={workspace_id}` и рендерит их.

#### Scenario: Список воркспейсов ещё грузится
- **WHEN** защищённый маршрут открыт, а `GET /api/workspaces` ещё не ответил
- **THEN** отображается полноэкранный индикатор загрузки, `children` не рендерятся

#### Scenario: У пользователя нет ни одного воркспейса
- **WHEN** `GET /api/workspaces` вернул пустой список
- **THEN** вместо `children` отображается пустое состояние с формой создания первого воркспейса

#### Scenario: Единственный воркспейс выбирается автоматически
- **WHEN** `GET /api/workspaces` вернул ровно один воркспейс, а сохранённого/валидного `workspace_id` в
  `localStorage` нет
- **THEN** `children` рендерятся сразу, обёрнутые в `WorkspaceContext.Provider` с этим воркспейсом, без показа
  списка выбора и без записи в `localStorage`

#### Scenario: Сохранённый воркспейс больше не существует (два и более воркспейса)
- **WHEN** в `localStorage` сохранён `workspace_id`, отсутствующий в списке из двух и более воркспейсов,
  полученном от `GET /api/workspaces`
- **THEN** отображается список существующих воркспейсов для выбора, `children` не рендерятся

#### Scenario: Валидный сохранённый воркспейс
- **WHEN** сохранённый `workspace_id` входит в список, полученный от `GET /api/workspaces`
- **THEN** `children` рендерятся, обёрнутые в `WorkspaceContext.Provider` с этим `workspace_id`

#### Scenario: Выбор воркспейса из списка сохраняет его
- **WHEN** пользователь выбирает воркспейс из списка, отображённого `RequireWorkspace`
- **THEN** выбранный `workspace_id` сохраняется в `localStorage`, `children` рендерятся с этим воркспейсом в
  `WorkspaceContext`

### Requirement: Сохранение выбора воркспейса в `localStorage`
Выбор текущего воркспейса SHALL сохраняться в `localStorage` под ключом `moneyhelper.workspace` — предпочтение
интерфейса (какой воркспейс открыт последним), а не данные пользователя или авторизации; хранилище-обёртка SHALL
не бросать исключение и не ломать приложение, если `localStorage` недоступен (приватный режим браузера и
подобное) — в этом случае выбор действует только до перезагрузки страницы.

#### Scenario: Выбор воркспейса переживает перезагрузку страницы
- **WHEN** пользователь выбрал воркспейс, затем перезагрузил страницу
- **THEN** приложение открывается с тем же воркспейсом, без повторного выбора

#### Scenario: Недоступное хранилище не ломает приложение
- **WHEN** `localStorage` недоступен (например, приватный режим браузера бросает исключение при обращении)
- **THEN** приложение продолжает работать, воркспейс выбирается заново при каждой загрузке страницы, без ошибки

### Requirement: Управление воркспейсами
Раздел «Настройки» SHALL содержать секцию управления воркспейсами: список всех воркспейсов пользователя
(`GET /api/workspaces`), для каждого — название, действие «Переключить» (недоступно для уже текущего воркспейса),
действие «Переименовать» (форма с одним полем названия, `PUT /api/workspaces/{id}`) и действие «Удалить»
(подтверждение `Popconfirm`, `DELETE /api/workspaces/{id}`, без предупреждения о содержимом — удаление воркспейса
на backend каскадное и безусловное), и действие создания нового воркспейса (`POST /api/workspaces`). Успешное
переключение SHALL обновить `WorkspaceContext` и сохранённый в `localStorage` `workspace_id` без перезагрузки
страницы; данные предыдущего воркспейса SHALL не отображаться после переключения (запросы, зависящие от
воркспейса, выполняются заново под новым `workspace_id`).

#### Scenario: Список воркспейсов в «Настройках»
- **WHEN** пользователь открывает «Настройки»
- **THEN** отображается секция со списком всех его воркспейсов и названием каждого

#### Scenario: Переключение воркспейса
- **WHEN** пользователь нажимает «Переключить» у воркспейса, отличного от текущего
- **THEN** этот воркспейс становится текущим (`WorkspaceContext` и `localStorage` обновлены), данные экранов
  (кошельки, категории, операции, переводы, аналитика) перезапрашиваются под новым `workspace_id`

#### Scenario: Переименование воркспейса
- **WHEN** пользователь переименовывает воркспейс через форму
- **THEN** запрос `PUT /api/workspaces/{id}` выполняется, список в «Настройках» отображает новое название

#### Scenario: Удаление воркспейса
- **WHEN** пользователь подтверждает удаление воркспейса, отличного от текущего
- **THEN** запрос `DELETE /api/workspaces/{id}` выполняется, воркспейс пропадает из списка

#### Scenario: Создание нового воркспейса из «Настроек»
- **WHEN** пользователь создаёт новый воркспейс через форму в секции управления
- **THEN** запрос `POST /api/workspaces` выполняется, новый воркспейс появляется в списке
