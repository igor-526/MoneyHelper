# analytics Specification

## Purpose
Отчёт по доходам и расходам воркспейса за необязательный диапазон дат (без него — за весь период), пересчитанный в выбранную валюту отображения и
сгруппированный по одной из четырёх осей (кошелёк, категория, валюта операции, календарный день в часовом поясе запроса). Единственный источник обменного курса
в системе — ноги пополнений (`topups`, категория `income`) того же воркспейса в валюте воркспейса и в валюте
кошелька; курс между парой валют — простое среднее по всем пополнениям воркспейса с ногами в обеих валютах за тот же
диапазон. Суммы по умолчанию выражены в валюте воркспейса. Валюты без найденного курса
исключаются из сумм без ошибки всего запроса и перечисляются в `unconverted_currencies`. Переводы (`transfers`) не
участвуют — они не доход и не расход. Данные и курс изолированы по воркспейсу (и транзитивно — по владельцу) на
уровне каждого запроса. Эндпоинт вложен под путь `/api/workspaces/{workspace_id}/analytics`.
## Requirements
### Requirement: Отчёт аналитики по операциям с группировкой
`GET /api/workspaces/{workspace_id}/analytics` SHALL возвращать суммы доходов и расходов указанного воркспейса,
принадлежащего текущему аутентифицированному пользователю, за явный диапазон дат `[date_from, date_to]`,
пересчитанные в валюту отображения `display_currency` (по умолчанию — валюта воркспейса), сгруппированные по одной
из четырёх осей `group_by` (`wallet` — по `wallet_id`, `category` — по `category_id`, `currency` — по валюте кошелька, `day` — по календарному дню операции в часовом поясе запроса).
`workspace_id` MUST принадлежать текущему пользователю. Каждая операция SHALL учитываться одной «ногой» — ногой в
валюте её кошелька; нога пополнения в валюте воркспейса (при отличающихся валютах) SHALL NOT учитываться, чтобы не
удваивать доход. Каждый элемент ответа (`buckets`) SHALL содержать `group_key` (для `day` — дата `YYYY-MM-DD`), `income` и `expense` — обе суммы
всегда присутствуют одновременно (`0`, если операций соответствующего типа в корзине нет). Корзины, для которых в
диапазоне (после всех фильтров) нет ни одной подходящей ноги операции, SHALL NOT включаться в ответ нулевой
записью. Аналитика охватывает только `transactions` указанного воркспейса (доходы — пополнения, расходы — через
`categories.type`); переводы (`transfers`) SHALL NOT учитываться ни в одной корзине. Ответ SHALL содержать
`display_currency_id` — валюту, в которой выражены суммы.

#### Scenario: Группировка по кошельку
- **WHEN** аутентифицированный пользователь запрашивает `GET
  /api/workspaces/{workspace_id}/analytics?group_by=wallet` с корректными `date_from`, `date_to`, и в диапазоне
  есть операции по нескольким кошелькам этого воркспейса
- **THEN** ответ 200 содержит по одной корзине `{group_key, income, expense}` на каждый кошелёк, по которому есть
  хотя бы одна операция в диапазоне, с суммами в валюте отображения

#### Scenario: Группировка по категории
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?group_by=category`, и в
  диапазоне есть операции по нескольким категориям этого воркспейса
- **THEN** ответ 200 содержит по одной корзине на каждую категорию, по которой есть хотя бы одна операция в
  диапазоне

#### Scenario: Группировка по валюте
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?group_by=currency`, и в
  диапазоне есть операции по кошелькам в нескольких валютах
- **THEN** ответ 200 содержит по одной корзине на каждую валюту кошельков (не валюту отображения), по которой
  есть хотя бы одна операция в диапазоне

#### Scenario: Обе суммы корзины присутствуют, даже если фильтр сузил выборку до одного типа
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?type=income` (или
  `type=expense`)
- **THEN** каждая корзина ответа 200 содержит и `income`, и `expense`; сторона, исключённая фильтром, равна `0`

#### Scenario: Пустые корзины не включаются в ответ
- **WHEN** в воркспейсе есть кошелёк/категория/валюта, по которым в диапазоне (с учётом прочих фильтров) нет ни
  одной операции
- **THEN** ответ 200 не содержит корзину с `group_key`, равным этому кошельку/категории/валюте

#### Scenario: Переводы не учитываются в аналитике
- **WHEN** в воркспейсе в диапазоне есть и операции, и переводы между его кошельками
- **THEN** суммы `income`/`expense` вычислены только по операциям; ни один перевод не влияет на суммы

#### Scenario: Пополнение с двумя ногами даёт один доход
- **WHEN** в диапазоне есть пополнение кошелька в валюте `C` воркспейса с валютой `W` с ногами `W` и `C`, и
  валюта отображения — `W`
- **THEN** в `income` вносится только сумма ноги `C`, пересчитанная в `W` по среднему курсу диапазона; нога `W`
  не добавляется второй раз

#### Scenario: Отклонение несуществующего или чужого воркспейса
- **WHEN** `GET /api/workspaces/{workspace_id}/analytics` отправлен с `workspace_id`, которого нет, либо
  принадлежащим другому пользователю
- **THEN** ответ 404

#### Scenario: Группировка по дням
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?group_by=day&type=expense`, и в
  диапазоне есть расходы в разные дни
- **THEN** ответ 200 содержит по одной корзине на каждый день с хотя бы одной операцией, `group_key` — дата
  `YYYY-MM-DD`, суммы в валюте отображения

#### Scenario: Дни считаются в часовом поясе запроса
- **WHEN** расход совершён в 22:00 UTC, и запрос `group_by=day` отправлен с `timezone=Europe/Moscow`
- **THEN** расход попадает в корзину следующего календарного дня; без `timezone` день считается по UTC

#### Scenario: Неизвестный часовой пояс
- **WHEN** запрос отправлен с `timezone`, которого нет в базе IANA
- **THEN** ответ 400

### Requirement: Конвертация сумм по среднему курсу диапазона
Сумма ноги операции, чья валюта совпадает с валютой отображения, SHALL включаться в корзину без конвертации.
Сумма ноги в другой валюте SHALL пересчитываться по курсу — простому среднему арифметическому значений
`target_leg.amount / source_leg.amount` по всем пополнениям того же воркспейса (операциям с категорией типа
`income`), содержащим ногу и в валюте ноги (`source`), и в валюте отображения (`target`), за тот же диапазон
`[date_from, date_to]`, что и запрос аналитики. Пополнения других воркспейсов в усреднении не участвуют.

#### Scenario: Расход в валюте кошелька пересчитывается в валюту воркспейса
- **WHEN** в воркспейсе (валюта `W`) в диапазоне есть одно пополнение кошелька в валюте `C` с ногами 10 000 `C` и
  780 `W`, и расход 1 000 `C`, валюта отображения — по умолчанию `W`
- **THEN** ответ 200 вносит расход `1000 × 0.078 = 78` `W`

#### Scenario: Курс усредняется по нескольким пополнениям
- **WHEN** в диапазоне есть два пополнения с ногами в одной паре валют, дающие два разных курса
- **THEN** используется простое среднее арифметическое этих курсов, а не средневзвешенное по суммам

#### Scenario: Валюта отображения не требует курса
- **WHEN** валюта отображения совпадает с валютой кошелька операции
- **THEN** сумма включается без пересчёта, курс не вычисляется

#### Scenario: Курс усредняется только по пополнениям диапазона
- **WHEN** пополнение с ногами пары валют лежит вне `[date_from, date_to]`
- **THEN** оно в усреднении не участвует

### Requirement: Обработка отсутствия курса для валюты
Суммы операции в валюте, для которой не найден курс к валюте отображения, SHALL исключаться из всех сумм ответа —
валюта считается неконвертируемой, если в диапазоне запроса нет ни одного пополнения того же воркспейса с ногой и
в этой валюте, и в валюте отображения; курс `1` SHALL NOT подставляться вместо отсутствующего. Валюта SHALL
добавляться в `unconverted_currencies` (список без дублей). Отсутствие курса для одной валюты SHALL NOT приводить к
ошибке всего запроса.

#### Scenario: Валюта без пополнений за диапазон остаётся неконвертируемой
- **WHEN** в диапазоне есть расход в валюте `C`, а пополнений с ногами `C` и валюты отображения в диапазоне нет
- **THEN** ответ 200 не включает расход ни в одну корзину, `unconverted_currencies` содержит `C`, остальные
  корзины рассчитаны как обычно

#### Scenario: Валюта с найденным курсом не попадает в unconverted_currencies
- **WHEN** в диапазоне есть операции в валюте с курсом и в валюте без курса
- **THEN** `unconverted_currencies` содержит только вторую валюту

### Requirement: Округление итоговых сумм корзины
Суммирование конвертированных сумм внутри каждой корзины SHALL выполняться в полной точности (без округления
промежуточных сумм ног). Округление до `decimal_places` валюты `display_currency` SHALL выполняться один раз — над
уже просуммированным итогом `income` и отдельно `expense` каждой корзины.

#### Scenario: Ошибки округления не накапливаются по множеству мелких операций
- **WHEN** в воркспейсе в диапазоне есть много операций в валюте, требующей конвертации, суммы которых по
  отдельности округлились бы по-разному, чем их сумма
- **THEN** ответ 200 содержит `income`/`expense` корзины, равные округлению суммы всех неокруглённых
  конвертированных сумм, а не сумме отдельно округлённых сумм каждой операции

### Requirement: Валидация валюты отображения
`display_currency` SHALL быть необязательным query-параметром; по умолчанию используется валюта воркспейса.
Допустимые значения — валюта воркспейса и валюта любого кошелька этого воркспейса. Любое другое значение
(неизвестная валюта или валюта, не связанная с воркспейсом) SHALL приводить к отклонению запроса с ответом 400.

#### Scenario: Валюта отображения по умолчанию — валюта воркспейса
- **WHEN** `GET /api/workspaces/{workspace_id}/analytics` отправлен без `display_currency`
- **THEN** ответ 200, `display_currency_id` равен валюте воркспейса

#### Scenario: Валюта кошелька допустима
- **WHEN** `display_currency` равна валюте одного из кошельков воркспейса
- **THEN** ответ 200 содержит суммы в этой валюте

#### Scenario: Неизвестная или посторонняя валюта отклоняется
- **WHEN** `display_currency` отсутствует в справочнике либо не является ни валютой воркспейса, ни валютой его
  кошелька
- **THEN** ответ 400 с понятным сообщением

### Requirement: Фильтры набора операций
`GET /api/workspaces/{workspace_id}/analytics` SHALL принимать опциональные query-параметры `wallet_id`,
`category_id`, `currency_id`, `type` (`income`/`expense`), сужающие набор операций, участвующих в агрегации.
`currency_id` соответствует валюте кошелька операции. Эти фильтры сужают только набор конвертируемых ног, но не
набор пополнений воркспейса, по которым усредняется курс.

#### Scenario: Фильтр по кошельку
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?wallet_id=...`
- **THEN** ответ 200 агрегирует только операции этого кошелька

#### Scenario: Фильтр по категории
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?category_id=...`
- **THEN** ответ 200 агрегирует только операции этой категории

#### Scenario: Фильтр по валюте кошелька
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?currency_id=...`
- **THEN** ответ 200 агрегирует только операции кошельков в этой валюте

#### Scenario: Фильтр по типу операции
- **WHEN** пользователь запрашивает `GET /api/workspaces/{workspace_id}/analytics?type=income` (или
  `type=expense`)
- **THEN** ответ 200 агрегирует только операции, чья категория имеет соответствующий `type`

#### Scenario: Фильтры не сужают набор пополнений для усреднения курса
- **WHEN** пользователь запрашивает аналитику с `wallet_id`, а пополнения, дающие курс, относятся к другим
  кошелькам воркспейса в том же диапазоне
- **THEN** курс, применённый к операциям отфильтрованного кошелька, всё равно вычислен по этим пополнениям

### Requirement: Изоляция данных по владельцу
Каждый расчёт `GET /api/workspaces/{workspace_id}/analytics` SHALL проверять принадлежность воркспейса текущему
пользователю и учитывать только операции и пополнения указанного воркспейса. Операции и пополнения другого
воркспейса (своего или чужого) MUST NOT участвовать ни в суммах, ни в усреднении курса.

#### Scenario: Чужие операции не участвуют в суммах
- **WHEN** пользователь запрашивает аналитику своего воркспейса, а в системе есть операции в других воркспейсах
- **THEN** суммы ответа 200 рассчитаны только по операциям запрошенного воркспейса

#### Scenario: Пополнение другого воркспейса не влияет на курс
- **WHEN** для валюты расхода в запрошенном воркспейсе нет пополнений с нужной парой, но в другом воркспейсе есть
- **THEN** валюта считается неконвертируемой и попадает в `unconverted_currencies`

#### Scenario: Отклонение несуществующего или чужого воркспейса
- **WHEN** `workspace_id` не существует либо принадлежит другому пользователю
- **THEN** ответ 404, данные не возвращаются

### Requirement: Отказ без аутентификации
`GET /api/workspaces/{workspace_id}/analytics` SHALL быть отклонён с ошибкой аутентификации при отсутствии
действительной сессии (access-cookie).

#### Scenario: Запрос без сессии отклоняется
- **WHEN** `GET /api/workspaces/{workspace_id}/analytics` отправлен без действительного access-cookie
- **THEN** ответ 401, данные не возвращаются

### Requirement: Необязательный диапазон дат
`date_from` и `date_to` SHALL быть необязательными query-параметрами `GET /api/workspaces/{workspace_id}/analytics`.
Отсутствующая граница SHALL означать отсутствие ограничения с этой стороны: без обоих параметров отчёт охватывает все
операции воркспейса, а курс усредняется по всем его пополнениям. Если заданы оба параметра и `date_from` позже
`date_to`, запрос SHALL быть отклонён.

#### Scenario: Запрос без диапазона охватывает весь период
- **WHEN** `GET /api/workspaces/{workspace_id}/analytics` отправлен без `date_from` и `date_to`, а операции лежат в
  разные месяцы
- **THEN** ответ 200 учитывает все операции воркспейса

#### Scenario: Задана одна граница
- **WHEN** `GET /api/workspaces/{workspace_id}/analytics` отправлен только с `date_to`
- **THEN** ответ 200 учитывает операции не позже `date_to`

#### Scenario: date_from позже date_to отклоняется
- **WHEN** заданы оба параметра и `date_from` позже `date_to`
- **THEN** ответ 400 с понятным сообщением

### Requirement: Часовой пояс запроса
Необязательный параметр `timezone` (имя IANA, по умолчанию `UTC`) SHALL задавать границы суток для среза `group_by=day`; на другие срезы и на границы `date_from`/`date_to` он не влияет.

#### Scenario: Значение по умолчанию
- **WHEN** запрос отправлен без `timezone`
- **THEN** сутки считаются по UTC
