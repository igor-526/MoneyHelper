# pwa Specification

## Purpose
PWA: manifest и иконки, service worker с кэшем только оболочки (API не кэшируется), обновление по подтверждению, индикатор офлайна, установка на домашний экран.
## Requirements
### Requirement: Web app manifest и иконки
Приложение SHALL публиковать web app manifest с полями: `name` («MoneyHelper»), `short_name`, `description` (русская), `lang: "ru"`, `start_url: "/"`, `scope: "/"`, `display: "standalone"`, `theme_color`, `background_color` и иконки: PNG 192×192 и 512×512 (`purpose: any`), 512×512 `purpose: maskable`. В `index.html` MUST быть подключён manifest, `apple-touch-icon` (180×180) и мета-теги `apple-mobile-web-app-capable`, `apple-mobile-web-app-title`, `apple-mobile-web-app-status-bar-style`. Иконки SHALL генерироваться из одного исходного SVG скриптом `npm run pwa-assets`, результат хранится в репозитории.

#### Scenario: Состав manifest
- **WHEN** тест читает конфигурацию manifest
- **THEN** присутствуют все перечисленные поля и иконки, а файлы иконок существуют в `public/`

#### Scenario: Maskable-иконка
- **WHEN** ОС обрезает иконку по маске
- **THEN** значимая часть иконки остаётся внутри безопасной зоны (иконка сгенерирована с полями)

### Requirement: Service worker и кэш оболочки
Приложение SHALL регистрировать service worker (сборка `vite-plugin-pwa`, Workbox), который предварительно кэширует оболочку приложения (HTML, JS, CSS, шрифты, иконки, manifest) и отдаёт `index.html` для навигационных запросов SPA. Приложение MUST открываться офлайн после первого успешного визита и показывать оболочку. Старые версии кэша SHALL очищаться при обновлении.

#### Scenario: Открытие офлайн
- **WHEN** пользователь один раз открыл приложение, затем отключил сеть и открыл его снова
- **THEN** оболочка приложения загружается из кэша

#### Scenario: Навигация SPA офлайн
- **WHEN** офлайн открывается маршрут SPA, например `/settings`
- **THEN** отдаётся `index.html`, роутер показывает страницу

### Requirement: Данные API не кэшируются
Service worker MUST NOT перехватывать и кэшировать запросы к API backend (в том числе `GET /health`) и ответы с авторизационными данными: запросы к API идут напрямую в сеть, а при отсутствии сети клиент получает сетевую ошибку и показывает toast «Нет соединения с сервером». Cookies и CORS-поведение запросов MUST NOT меняться.

#### Scenario: Запрос к API офлайн
- **WHEN** приложение офлайн вызывает API
- **THEN** запрос завершается сетевой ошибкой `ApiError(kind = "network")`, а не устаревшим ответом из кэша

#### Scenario: Конфигурация кэша
- **WHEN** тест проверяет конфигурацию service worker
- **THEN** в ней нет правил runtime-кэширования запросов к адресу из `VITE_API_URL`

### Requirement: Обновление версии
Service worker SHALL работать в режиме подтверждения обновления (`registerType: "prompt"`): когда доступна новая версия, приложение показывает баннер «Доступна новая версия» с кнопкой «Обновить»; по нажатию новая версия активируется и страница перезагружается. Новая версия MUST NOT применяться автоматически посреди работы пользователя (например, при заполнении формы). Баннер расположен выше нижней панели навигации и учитывает безопасные зоны.

#### Scenario: Новая версия
- **WHEN** service worker сообщает о доступной новой версии
- **THEN** показывается баннер с кнопкой «Обновить», страница не перезагружается сама

#### Scenario: Подтверждение
- **WHEN** пользователь нажимает «Обновить»
- **THEN** вызывается активация новой версии

### Requirement: Индикатор офлайн
Приложение SHALL следить за `navigator.onLine` и событиями `online`/`offline` и при отсутствии сети показывать заметный баннер «Нет соединения. Данные могут быть недоступны», скрывая его при восстановлении сети. Баннер MUST NOT заменять обработку ошибок API: каждая сетевая ошибка запроса по-прежнему приводит к toast.

#### Scenario: Пропала сеть
- **WHEN** срабатывает событие `offline`
- **THEN** показывается баннер офлайн

#### Scenario: Сеть вернулась
- **WHEN** срабатывает событие `online`
- **THEN** баннер скрывается

### Requirement: Установка на домашний экран
Приложение SHALL перехватывать событие `beforeinstallprompt` и на странице настроек показывать кнопку «Установить приложение», вызывающую системный диалог установки; после установки или в режиме `standalone` кнопка скрыта. На iOS Safari, где события нет, страница настроек SHALL показывать краткую инструкцию «Поделиться → На экран Домой». Логика SHALL быть в хуке `useInstallPrompt`, отделённом от UI.

#### Scenario: Установка доступна
- **WHEN** браузер отправил `beforeinstallprompt`
- **THEN** на странице настроек показывается кнопка «Установить приложение»

#### Scenario: Уже установлено
- **WHEN** приложение открыто в режиме `standalone`
- **THEN** кнопка установки и инструкция не показываются

#### Scenario: iOS
- **WHEN** приложение открыто в Safari на iOS и не установлено
- **THEN** показывается инструкция по добавлению на экран «Домой»

### Requirement: Режим standalone
В режиме `standalone` layout SHALL корректно учитывать безопасные зоны и отсутствие адресной строки (`100dvh`, `env(safe-area-inset-*)`), а мобильные и тёмные правила MUST действовать так же, как в браузере.

#### Scenario: Запуск с домашнего экрана
- **WHEN** приложение запущено в режиме `standalone` на телефоне
- **THEN** нижняя панель и контент не пересекаются с системными зонами экрана
