# workspaces Specification

## Purpose
Реестр рабочих пространств (воркспейсов) пользователя: создание, чтение одного/списка с пагинацией, полная замена
названия (`PUT`) и физическое удаление. Каждый воркспейс принадлежит ровно одному пользователю, без совместного
доступа, ролей и приглашений. Воркспейс — единица полной изоляции для кошельков, категорий, операций, переводов и
производных от них (балансов, аналитики): все вложенные ресурсы живут под путём
`/api/workspaces/{workspace_id}/...`, а данные разных воркспейсов одного пользователя нигде не смешиваются — так
же, как сейчас изолированы данные разных пользователей. Удаление воркспейса — физическое и каскадное: в отличие от
удаления кошелька или категории, оно не блокируется наличием связанных данных, а безусловно удаляет всё вложенное.

## Requirements
### Requirement: Создание воркспейса
`POST /api/workspaces` SHALL создавать рабочее пространство (воркспейс), принадлежащее текущему аутентифицированному
пользователю, с названием. Совместный доступ нескольких пользователей к одному воркспейсу не поддерживается —
воркспейс принадлежит ровно одному пользователю. Запрос без действительной сессии (без access-cookie) SHALL быть
отклонён с ошибкой аутентификации.

#### Scenario: Успешное создание воркспейса
- **WHEN** аутентифицированный пользователь отправляет `POST /api/workspaces` с корректным `name`
- **THEN** ответ 201 содержит созданный воркспейс с этим `id`, `name`, `created_at` и `updated_at`

#### Scenario: Отклонение пустого названия
- **WHEN** `POST /api/workspaces` отправлен с `name`, состоящим только из пробелов или пустой строкой
- **THEN** ответ 400 с ошибкой валидации, воркспейс не создаётся

#### Scenario: Названия воркспейсов не обязаны быть уникальными
- **WHEN** у пользователя уже есть воркспейс с названием «Поездка», и он отправляет `POST /api/workspaces` с тем же
  `name = "Поездка"`
- **THEN** ответ 201, оба воркспейса существуют одновременно с разными `id`

#### Scenario: Отказ без аутентификации
- **WHEN** `POST /api/workspaces` отправлен без действительного access-cookie
- **THEN** ответ 401, воркспейс не создаётся

### Requirement: Список воркспейсов пользователя
`GET /api/workspaces` SHALL возвращать постраничный список воркспейсов, принадлежащих только текущему
аутентифицированному пользователю, отсортированный по `created_at` по возрастанию, затем по `id` как
детерминированному tie-breaker. Параметры пагинации — `limit` (1..100, по умолчанию 20) и `offset` (≥ 0, по
умолчанию 0).

#### Scenario: Список содержит только воркспейсы текущего пользователя
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/workspaces`, при этом в системе есть воркспейсы,
  принадлежащие другим пользователям
- **THEN** ответ 200 содержит только воркспейсы текущего пользователя, `total` равен числу его воркспейсов

#### Scenario: Порядок списка детерминирован
- **WHEN** у пользователя есть несколько воркспейсов
- **THEN** ответ 200 возвращает их отсортированными по `created_at` по возрастанию, а при равном `created_at` — по
  `id` по возрастанию

#### Scenario: Пагинация по умолчанию
- **WHEN** `GET /api/workspaces` запрошен без параметров `limit`/`offset`
- **THEN** ответ 200 использует `limit = 20`, `offset = 0`

#### Scenario: Недопустимые параметры пагинации отклоняются
- **WHEN** `GET /api/workspaces` запрошен с `limit` вне диапазона 1..100 или с отрицательным `offset`
- **THEN** ответ 400 с ошибкой валидации

### Requirement: Чтение одного воркспейса
`GET /api/workspaces/{workspace_id}` SHALL возвращать воркспейс по `id`, только если он принадлежит текущему
аутентифицированному пользователю.

#### Scenario: Успешное чтение своего воркспейса
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/workspaces/{workspace_id}` для своего воркспейса
- **THEN** ответ 200 содержит `id`, `name`, `created_at`, `updated_at`

#### Scenario: Несуществующий воркспейс
- **WHEN** запрашивается `GET /api/workspaces/{workspace_id}` с `workspace_id`, которого нет ни у одного
  пользователя
- **THEN** ответ 404

### Requirement: Полное обновление воркспейса
`PUT /api/workspaces/{workspace_id}` SHALL полностью заменять `name` воркспейса, принадлежащего текущему
аутентифицированному пользователю. Частичное обновление (`PATCH`) не поддерживается.

#### Scenario: Успешная полная замена
- **WHEN** аутентифицированный пользователь отправляет `PUT /api/workspaces/{workspace_id}` для своего воркспейса с
  новым корректным `name`
- **THEN** ответ 200 содержит воркспейс с обновлённым `name` и обновлённым `updated_at`

#### Scenario: Обновление несуществующего воркспейса
- **WHEN** `PUT /api/workspaces/{workspace_id}` отправлен с `workspace_id`, которого нет ни у одного пользователя
- **THEN** ответ 404, изменения не применяются

#### Scenario: Обновление с той же валидацией входных данных, что и создание
- **WHEN** `PUT /api/workspaces/{workspace_id}` отправлен с `name`, состоящим только из пробелов или пустой строкой
- **THEN** ответ 400, изменения не применяются

### Requirement: Удаление воркспейса
`DELETE /api/workspaces/{workspace_id}` SHALL физически удалять воркспейс, принадлежащий текущему
аутентифицированному пользователю, вместе со всеми вложенными данными (кошельками, категориями, операциями,
переводами) каскадно, без предварительной проверки на существование этих данных. В отличие от удаления кошелька
или категории, удаление воркспейса SHALL NOT отклоняться из-за наличия связанных данных.

#### Scenario: Успешное удаление пустого воркспейса
- **WHEN** аутентифицированный пользователь отправляет `DELETE /api/workspaces/{workspace_id}` для своего
  воркспейса, в котором ещё нет ни кошельков, ни категорий, ни операций, ни переводов
- **THEN** ответ 204, воркспейс удалён; последующий `GET /api/workspaces/{workspace_id}` для того же `id`
  возвращает 404

#### Scenario: Удаление непустого воркспейса каскадно удаляет вложенные данные
- **WHEN** аутентифицированный пользователь отправляет `DELETE /api/workspaces/{workspace_id}` для своего
  воркспейса, в котором есть кошельки, категории, операции и переводы
- **THEN** ответ 204; воркспейс, все его кошельки, категории, операции и переводы удалены; последующий
  `GET /api/workspaces/{workspace_id}/wallets` (и аналогично для категорий/операций/переводов) для того же
  `workspace_id` возвращает 404 на уровне самого воркспейса

#### Scenario: Удаление несуществующего воркспейса
- **WHEN** `DELETE /api/workspaces/{workspace_id}` отправлен с `workspace_id`, которого нет ни у одного
  пользователя
- **THEN** ответ 404

### Requirement: Изоляция данных по владельцу
Каждый эндпоинт, оперирующий воркспейсом, SHALL проверять принадлежность воркспейса текущему аутентифицированному
пользователю на уровне запроса к данным. Это касается и эндпоинтов самого воркспейса (`GET`, `PUT`, `DELETE
/api/workspaces/{workspace_id}`), и любого вложенного эндпоинта под ним (кошельки, категории, операции, переводы,
балансы, аналитика — любой путь вида `/api/workspaces/{workspace_id}/...`); проверка выполняется на уровне запроса
к данным, не отдельной проверкой после чтения. Воркспейс, принадлежащий другому пользователю, MUST быть неотличим
снаружи от несуществующего: в обоих случаях SHALL возвращаться 404, а не 403, для самого воркспейса и для любого
вложенного ресурса под ним.

#### Scenario: Чужой воркспейс недоступен для чтения
- **WHEN** пользователь A запрашивает `GET /api/workspaces/{workspace_id}` с `workspace_id` воркспейса,
  принадлежащего пользователю B
- **THEN** ответ 404, а не 403; данные воркспейса B не раскрываются

#### Scenario: Чужой воркспейс недоступен для обновления
- **WHEN** пользователь A отправляет `PUT /api/workspaces/{workspace_id}` с `workspace_id` воркспейса,
  принадлежащего пользователю B
- **THEN** ответ 404, воркспейс B не изменяется

#### Scenario: Чужой воркспейс недоступен для удаления
- **WHEN** пользователь A отправляет `DELETE /api/workspaces/{workspace_id}` с `workspace_id` воркспейса,
  принадлежащего пользователю B
- **THEN** ответ 404, воркспейс B не удаляется

#### Scenario: Вложенные ресурсы чужого воркспейса недоступны
- **WHEN** пользователь A запрашивает любой вложенный эндпоинт (например, `GET
  /api/workspaces/{workspace_id}/wallets`) с `workspace_id` воркспейса, принадлежащего пользователю B
- **THEN** ответ 404, данные внутри воркспейса B не раскрываются, независимо от того, есть ли у пользователя A
  собственные кошельки с такими же `id`
