## Context

Из 026 уже есть: `/transactions` работает только с расходами (категория `expense` проверяется при `POST`/`PUT`,
`get/update/delete/list` видят только расходы через `get_of_type` и `type=EXPENSE`), одна нога, комментарий (022),
фильтры списка `wallet_id`, `category_id`, `date_from`, `date_to` и пагинация `Page`, параметра `type` нет.
Из 025: у кошелька одна валюта `wallet.currency_id`, набора валют и правила «валюта входит в набор» нет; сервис
сверяет `currency_id` запроса с валютой кошелька. Баланс кошелька считает ноги в валюте кошелька.

## Что уже сделано в 026 и не меняется

- Категория расхода обязана быть `expense` (400 на `income`), раздельные списки пополнений и расходов.
- Список с фильтрами и пагинацией, `GET/PUT/DELETE` только для расходов (пополнение — 404).
- Комментарий, нормализация пробельного `comment` в `null`, лимит 1000 символов.
- Баланс и аналитика: расход — одна отрицательная нога в валюте кошелька, изменений не требуется.

## Goals / Non-Goals

**Goals:**
- Расход создаётся и обновляется без валюты в запросе; нога получает `wallet.currency_id`.
- Контракт расхода зафиксирован тестами (unit, API, smoke, infrastructure).

**Non-Goals:**
- Новая схема БД, пополнения, переводы, аналитика, frontend.

## Decisions

1. **Форма эндпоинтов остаётся: `/api/workspaces/{workspace_id}/transactions`.** Вопрос «`/expenses` или
   `/transactions` с фильтром» закрыт в 026: вид операции задаёт тип категории, а ресурсы разделены
   (`/topups` и `/transactions`) без ветвления `if type == ...` (`get_of_type` + тип в фильтре репозитория).
   Переименование в `/expenses` не даёт выгоды и ломало бы контракт второй раз; ресурс остаётся «расходами» по
   смыслу, это зафиксировано в спецификации `transactions`.

2. **Валюта берётся из кошелька.** `TransactionService.create_transaction/update_transaction` перестают принимать
   `currency_id`; нога = `TransactionLeg(currency_id=wallet.currency_id, amount)`. Валидация входа
   (`_validate_transaction_input`) возвращает кошелёк и использует его валюту для `validate_leg_amount`
   (положительность, существование валюты, точность по `decimal_places`). Проверка совпадения валют удалена.

3. **Схема запроса.** `TransactionCreate` теряет `currency_id` и получает `extra="forbid"`: клиент, всё ещё
   передающий `currency_id`, получает явный 400, а не молчаливое игнорирование (тихо проигнорированная валюта
   вводила бы в заблуждение). `TransactionUpdate = TransactionCreate` как прежде.

4. **Ответ не меняется:** `legs` — список из одной ноги, чтобы не ломать форму чтения операции (frontend
   адаптируется в 033). Отдельное поле `currency_id` не добавляется (избыточно с `legs[0]`).

5. **Баланс в минус не запрещён.** Поведение сохраняется; вопрос не стал значимым.

6. **Миграций нет.**

## Risks / Trade-offs

- Контракт `POST`/`PUT` ломается (убрано `currency_id`, лишние поля — 400); frontend несовместим до 033 (по плану
  после backend).
- Данные расходов с чужой валютой невозможны: валюта кошелька неизменна при наличии операций (025), нога всегда в
  валюте кошелька.
