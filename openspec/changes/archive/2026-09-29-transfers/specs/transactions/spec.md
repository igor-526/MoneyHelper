## MODIFIED Requirements

### Requirement: Создание операции
`POST /api/transactions` SHALL создавать операцию (доход или расход) с ровно одной «ногой» (валюта + сумма),
принадлежащую текущему аутентифицированному пользователю, с указанием кошелька, категории, валюты и положительной
суммы. Кошелёк и категория MUST принадлежать текущему пользователю. Валюта операции MUST входить в набор валют
указанного кошелька. Число знаков после запятой суммы MUST NOT превышать `decimal_places` валюты; округление не
выполняется. `occurred_at` — опциональное поле; при отсутствии SHALL использоваться текущее время сервера. Запрос
без действительной сессии (без access-cookie) SHALL быть отклонён с ошибкой аутентификации. Ответ представляет
операцию в ногозависимой форме: `legs` — список из одного элемента `{currency_id, amount}`.

#### Scenario: Успешное создание операции с указанной датой
- **WHEN** аутентифицированный пользователь отправляет `POST /api/transactions` с корректными `wallet_id`
  (своего кошелька), `category_id` (своей категории), `currency_id` из набора валют кошелька, положительным
  `amount` с числом знаков не более `decimal_places` валюты и явным `occurred_at`
- **THEN** ответ 201 содержит созданную операцию с этим `id`, `wallet_id`, `category_id`, `legs` (список из одного
  элемента с этими `currency_id` и `amount`), `occurred_at` (равным переданному), `created_at` и `updated_at`

#### Scenario: Успешное создание операции без даты — используется текущее время
- **WHEN** `POST /api/transactions` отправлен без поля `occurred_at`
- **THEN** ответ 201 содержит операцию с `occurred_at`, равным текущему времени сервера на момент создания

#### Scenario: Отклонение валюты, не входящей в набор валют кошелька
- **WHEN** `POST /api/transactions` отправлен с `currency_id`, отсутствующим в `currency_ids` указанного кошелька
- **THEN** ответ 400 с понятным сообщением, операция не создаётся

#### Scenario: Отклонение суммы с превышением числа знаков валюты
- **WHEN** `POST /api/transactions` отправлен с `amount`, число знаков после запятой которого превышает
  `decimal_places` валюты `currency_id`
- **THEN** ответ 400, операция не создаётся, сумма не округляется

#### Scenario: Отклонение неположительной суммы
- **WHEN** `POST /api/transactions` отправлен с `amount`, равным нулю или отрицательным
- **THEN** ответ 400 с ошибкой валидации, операция не создаётся

#### Scenario: Отклонение несуществующего или чужого кошелька
- **WHEN** `POST /api/transactions` отправлен с `wallet_id`, которого нет ни у одного пользователя, либо
  принадлежащим другому пользователю
- **THEN** ответ 404, операция не создаётся

#### Scenario: Отклонение несуществующей или чужой категории
- **WHEN** `POST /api/transactions` отправлен с `category_id`, которой нет ни у одного пользователя, либо
  принадлежащей другому пользователю
- **THEN** ответ 404, операция не создаётся

#### Scenario: Отказ без аутентификации
- **WHEN** `POST /api/transactions` отправлен без действительного access-cookie
- **THEN** ответ 401, операция не создаётся

### Requirement: Список операций пользователя с фильтрами и сортировкой
`GET /api/transactions` SHALL возвращать постраничный список операций, принадлежащих только текущему
аутентифицированному пользователю, отсортированный по `occurred_at` по убыванию, затем по `id` по убыванию как
детерминированному tie-breaker (новые операции первыми). Опциональные query-параметры `wallet_id`, `category_id`,
`type` (`income`/`expense`, через тип связанной категории), `date_from` и `date_to` (включительно, диапазон по
`occurred_at`) SHALL сужать список. Если заданы оба `date_from` и `date_to`, и `date_from` позже `date_to`, запрос
SHALL быть отклонён. Параметры пагинации — `limit` (1..100, по умолчанию 20) и `offset` (≥ 0, по умолчанию 0).
Каждый элемент списка представляет операцию в ногозависимой форме (`legs`) — как обычные операции (список из
одного элемента), так и пополнения (список из нескольких элементов), без отдельного признака различия.

#### Scenario: Список содержит только операции текущего пользователя
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/transactions`, при этом в системе есть операции,
  принадлежащие другим пользователям
- **THEN** ответ 200 содержит только операции текущего пользователя, `total` равен числу его операций

#### Scenario: Порядок списка — новые операции первыми
- **WHEN** у пользователя есть несколько операций с разными `occurred_at`
- **THEN** ответ 200 возвращает их отсортированными по `occurred_at` по убыванию, а при равном `occurred_at` — по
  `id` по убыванию

#### Scenario: Фильтр по кошельку
- **WHEN** пользователь запрашивает `GET /api/transactions?wallet_id=...` для одного из своих кошельков
- **THEN** ответ 200 содержит только операции этого кошелька

#### Scenario: Фильтр по категории
- **WHEN** пользователь запрашивает `GET /api/transactions?category_id=...` для одной из своих категорий
- **THEN** ответ 200 содержит только операции этой категории

#### Scenario: Фильтр по типу операции
- **WHEN** пользователь запрашивает `GET /api/transactions?type=income` (или `type=expense`)
- **THEN** ответ 200 содержит только операции, чья категория имеет соответствующий `type`

#### Scenario: Фильтр по диапазону дат
- **WHEN** пользователь запрашивает `GET /api/transactions?date_from=...&date_to=...`
- **THEN** ответ 200 содержит только операции с `occurred_at` в указанном диапазоне включительно

#### Scenario: Некорректный диапазон дат отклоняется
- **WHEN** `GET /api/transactions?date_from=...&date_to=...` запрошен с `date_from`, позже `date_to`
- **THEN** ответ 400 с ошибкой валидации

#### Scenario: Пагинация по умолчанию
- **WHEN** `GET /api/transactions` запрошен без параметров `limit`/`offset`
- **THEN** ответ 200 использует `limit = 20`, `offset = 0`

#### Scenario: Недопустимые параметры пагинации отклоняются
- **WHEN** `GET /api/transactions` запрошен с `limit` вне диапазона 1..100 или с отрицательным `offset`
- **THEN** ответ 400 с ошибкой валидации

#### Scenario: Список отображает пополнение с несколькими ногами
- **WHEN** у пользователя есть операция-пополнение (созданная через `POST /api/transactions/topups`) с несколькими
  валютами
- **THEN** соответствующий элемент списка `GET /api/transactions` содержит `legs` со всеми ногами этого пополнения

### Requirement: Чтение одной операции
`GET /api/transactions/{transaction_id}` SHALL возвращать операцию по `id`, только если она принадлежит текущему
аутентифицированному пользователю. Ответ представляет операцию в ногозависимой форме: `legs` — список из одного
элемента `{currency_id, amount}` для обычной операции или из нескольких элементов для пополнения; по числу
элементов `legs` пополнение отличимо от обычной операции, отдельного признака типа нет.

#### Scenario: Успешное чтение своей операции
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/transactions/{transaction_id}` для своей
  операции
- **THEN** ответ 200 содержит `id`, `wallet_id`, `category_id`, `legs`, `occurred_at`, `created_at`, `updated_at`

#### Scenario: Чтение пополнения возвращает все его ноги
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/transactions/{transaction_id}` для своего
  пополнения с несколькими валютами
- **THEN** ответ 200 содержит `legs` со всеми ногами пополнения, отсортированными по коду валюты

#### Scenario: Несуществующая операция
- **WHEN** запрашивается `GET /api/transactions/{transaction_id}` с `transaction_id`, которого нет ни у одного
  пользователя
- **THEN** ответ 404

### Requirement: Полное обновление операции
`PUT /api/transactions/{transaction_id}` SHALL полностью заменять `wallet_id`, `category_id`, `currency_id`,
`amount` и `occurred_at` операции, принадлежащей текущему аутентифицированному пользователю, с той же валидацией,
что и при создании. Результат всегда содержит ровно одну ногу — `PUT` не поддерживает многовалютные операции
(пополнение с несколькими ногами нельзя отредактировать через `PUT`; изменить его можно только удалением через
`DELETE /api/transactions/{transaction_id}` и созданием заново через `POST /api/transactions/topups`). Частичное
обновление (`PATCH`) не поддерживается.

#### Scenario: Успешная полная замена
- **WHEN** аутентифицированный пользователь отправляет `PUT /api/transactions/{transaction_id}` для своей операции
  с новыми корректными `wallet_id`, `category_id`, `currency_id`, `amount` и `occurred_at`
- **THEN** ответ 200 содержит операцию с `legs` — списком из одного элемента с обновлёнными `currency_id`/
  `amount`, и обновлённым `updated_at`

#### Scenario: Обновление несуществующей операции
- **WHEN** `PUT /api/transactions/{transaction_id}` отправлен с `transaction_id`, которого нет ни у одного
  пользователя
- **THEN** ответ 404, изменения не применяются

#### Scenario: Обновление с той же валидацией входных данных, что и создание
- **WHEN** `PUT /api/transactions/{transaction_id}` отправлен с валютой, не входящей в набор валют кошелька,
  неположительной суммой, суммой с превышением знаков валюты, либо несуществующим/чужим `wallet_id` или
  `category_id`
- **THEN** ответ 400 или 404 (в зависимости от причины), изменения не применяются

#### Scenario: Полная замена превращает пополнение в операцию с одной ногой
- **WHEN** аутентифицированный пользователь отправляет `PUT /api/transactions/{transaction_id}` для своего
  пополнения (ранее имевшего несколько ног) с новыми корректными `wallet_id`, `category_id`, `currency_id`,
  `amount` и `occurred_at`
- **THEN** ответ 200 содержит операцию с `legs` — списком ровно из одного элемента; прежние ноги пополнения
  заменены полностью

### Requirement: Баланс по кошельку и валюте
`GET /api/wallets/{wallet_id}/balances` SHALL возвращать баланс кошелька, принадлежащего текущему
аутентифицированному пользователю, по каждой валюте из набора валют кошелька (включая валюты без единой операции
и перевода — с балансом 0), отсортированный по коду валюты. Баланс по валюте вычисляется на лету как сумма вклада
всех источников: операций (сумма `amount` операций с категорией типа `income` минус сумма `amount` операций с
категорией типа `expense`) и переводов (сумма `amount` переводов, у которых кошелёк — `to_wallet_id`, минус сумма
`amount` переводов, у которых кошелёк — `from_wallet_id`), отфильтрованных по этому кошельку, валюте и
пользователю.

#### Scenario: Баланс кошелька без операций и переводов — нули по всем его валютам
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/wallets/{wallet_id}/balances` для своего
  кошелька, у которого ещё нет ни одной операции и ни одного перевода
- **THEN** ответ 200 содержит запись с `balance = 0` для каждой валюты из `currency_ids` этого кошелька

#### Scenario: Баланс учитывает доходы и расходы
- **WHEN** у кошелька есть операции дохода на сумму X и операции расхода на сумму Y в одной и той же валюте
- **THEN** ответ 200 содержит баланс, равный X минус Y, для этой валюты

#### Scenario: Баланс учитывает переводы
- **WHEN** у кошелька есть перевод на сумму Z, в котором кошелёк — целевой (`to_wallet_id`), и перевод на сумму W,
  в котором кошелёк — исходный (`from_wallet_id`), в одной и той же валюте
- **THEN** ответ 200 содержит баланс по этой валюте, увеличенный на Z и уменьшенный на W относительно баланса без
  этих переводов

#### Scenario: Баланс отдельен по валютам многовалютного кошелька
- **WHEN** у кошелька с несколькими валютами есть операции и переводы в разных валютах
- **THEN** ответ 200 содержит отдельную запись `{currency_id, balance}` для каждой валюты кошелька, не смешивая
  суммы разных валют

#### Scenario: Несуществующий или чужой кошелёк
- **WHEN** запрашивается `GET /api/wallets/{wallet_id}/balances` с `wallet_id`, которого нет ни у одного
  пользователя, либо принадлежащим другому пользователю
- **THEN** ответ 404

## ADDED Requirements

### Requirement: Пополнение многовалютного кошелька
`POST /api/transactions/topups` SHALL создавать операцию пополнения — доход, принадлежащий текущему
аутентифицированному пользователю, с несколькими «ногами» (валюта + сумма), одной на каждую валюту указанного
кошелька. Кошелёк и категория MUST принадлежать текущему пользователю. Категория MUST иметь тип `income`. Набор
валют переданных ног MUST совпадать ровно с набором валют кошелька (`wallet.currency_ids`) — без отсутствующих,
без лишних, без повторов. Каждая сумма MUST быть положительной, число знаков после запятой MUST NOT превышать
`decimal_places` соответствующей валюты; округление не выполняется. Курс между валютами пополнения не хранится
отдельным полем — воспроизводим как отношение сохранённых сумм ног. `occurred_at` — опциональное поле; при
отсутствии SHALL использоваться текущее время сервера. Запрос без действительной сессии (без access-cookie) SHALL
быть отклонён с ошибкой аутентификации.

#### Scenario: Успешное пополнение с полным набором валют кошелька
- **WHEN** аутентифицированный пользователь отправляет `POST /api/transactions/topups` с `wallet_id` своего
  многовалютного кошелька, `category_id` своей категории типа `income` и `legs`, содержащими ровно по одной ноге
  на каждую валюту кошелька с положительными суммами без превышения знаков после запятой
- **THEN** ответ 201 содержит созданную операцию с этим `id`, `wallet_id`, `category_id`, `legs` (все переданные
  валюты и суммы, отсортированные по коду валюты), `occurred_at`, `created_at` и `updated_at`

#### Scenario: Успешное пополнение без даты — используется текущее время
- **WHEN** `POST /api/transactions/topups` отправлен без поля `occurred_at`
- **THEN** ответ 201 содержит операцию с `occurred_at`, равным текущему времени сервера на момент создания

#### Scenario: Курс воспроизводим по сохранённым ногам
- **WHEN** пополнение создано с ногами, например, 10 000 в одной валюте и 780 в другой
- **THEN** после создания курс между этими валютами вычислим как отношение сохранённых сумм ног (10 000 / 780) без
  отдельно хранимого значения курса

#### Scenario: Отклонение пополнения с неполным набором валют
- **WHEN** `POST /api/transactions/topups` отправлен для многовалютного кошелька с `legs`, не содержащими ногу
  хотя бы для одной из валют кошелька
- **THEN** ответ 400 с сообщением, перечисляющим отсутствующие валюты, операция не создаётся

#### Scenario: Отклонение пополнения с избыточным набором валют
- **WHEN** `POST /api/transactions/topups` отправлен с `legs`, содержащими валюту, отсутствующую в наборе валют
  указанного кошелька
- **THEN** ответ 400 с сообщением, перечисляющим лишние валюты, операция не создаётся

#### Scenario: Отклонение пополнения с повторяющейся валютой в ногах
- **WHEN** `POST /api/transactions/topups` отправлен с `legs`, содержащими одну и ту же валюту более одного раза
- **THEN** ответ 400 с ошибкой валидации, операция не создаётся

#### Scenario: Отклонение пополнения с категорией не типа income
- **WHEN** `POST /api/transactions/topups` отправлен с `category_id` категории типа `expense`
- **THEN** ответ 400 с понятным сообщением, операция не создаётся

#### Scenario: Отклонение неположительной суммы в ноге пополнения
- **WHEN** `POST /api/transactions/topups` отправлен с хотя бы одной ногой, у которой `amount` равен нулю или
  отрицателен
- **THEN** ответ 400 с ошибкой валидации, операция не создаётся

#### Scenario: Отклонение суммы с превышением числа знаков валюты в ноге пополнения
- **WHEN** `POST /api/transactions/topups` отправлен с хотя бы одной ногой, у которой число знаков после запятой
  `amount` превышает `decimal_places` соответствующей валюты
- **THEN** ответ 400, операция не создаётся, сумма не округляется

#### Scenario: Отклонение несуществующего или чужого кошелька
- **WHEN** `POST /api/transactions/topups` отправлен с `wallet_id`, которого нет ни у одного пользователя, либо
  принадлежащим другому пользователю
- **THEN** ответ 404, операция не создаётся

#### Scenario: Отклонение несуществующей или чужой категории
- **WHEN** `POST /api/transactions/topups` отправлен с `category_id`, которой нет ни у одного пользователя, либо
  принадлежащей другому пользователю
- **THEN** ответ 404, операция не создаётся

#### Scenario: Отказ без аутентификации
- **WHEN** `POST /api/transactions/topups` отправлен без действительного access-cookie
- **THEN** ответ 401, операция не создаётся
