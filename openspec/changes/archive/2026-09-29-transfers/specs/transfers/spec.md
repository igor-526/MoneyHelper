## ADDED Requirements

### Requirement: Создание перевода
`POST /api/transfers` SHALL создавать перевод денежных средств между двумя разными кошельками текущего
аутентифицированного пользователя в одной валюте, без конвертации. `from_wallet_id` и `to_wallet_id` MUST
принадлежать текущему пользователю и MUST NOT совпадать. `currency_id` MUST входить в набор валют одновременно
`from_wallet_id` И `to_wallet_id`. Сумма MUST быть положительной, число знаков после запятой MUST NOT превышать
`decimal_places` валюты; округление не выполняется. `occurred_at` — опциональное поле; при отсутствии SHALL
использоваться текущее время сервера. Запрос без действительной сессии (без access-cookie) SHALL быть отклонён с
ошибкой аутентификации.

#### Scenario: Успешное создание перевода
- **WHEN** аутентифицированный пользователь отправляет `POST /api/transfers` с корректными `from_wallet_id` и
  `to_wallet_id` (оба — свои кошельки, разные), `currency_id`, входящим в набор валют обоих кошельков,
  положительным `amount` с числом знаков не более `decimal_places` валюты и явным `occurred_at`
- **THEN** ответ 201 содержит созданный перевод с этим `id`, `from_wallet_id`, `to_wallet_id`, `currency_id`,
  `amount`, `occurred_at` (равным переданному), `created_at` и `updated_at`

#### Scenario: Успешное создание перевода без даты — используется текущее время
- **WHEN** `POST /api/transfers` отправлен без поля `occurred_at`
- **THEN** ответ 201 содержит перевод с `occurred_at`, равным текущему времени сервера на момент создания

#### Scenario: Отклонение перевода без общей валюты у кошельков
- **WHEN** `POST /api/transfers` отправлен с `currency_id`, отсутствующим в наборе валют `from_wallet_id` или
  отсутствующим в наборе валют `to_wallet_id` (включая случай, когда у кошельков вовсе нет общей валюты)
- **THEN** ответ 400 с понятным сообщением, перевод не создаётся

#### Scenario: Отклонение перевода самому себе
- **WHEN** `POST /api/transfers` отправлен с одинаковыми `from_wallet_id` и `to_wallet_id`
- **THEN** ответ 400 с ошибкой валидации, перевод не создаётся

#### Scenario: Отклонение несуществующего или чужого исходного кошелька
- **WHEN** `POST /api/transfers` отправлен с `from_wallet_id`, которого нет ни у одного пользователя, либо
  принадлежащим другому пользователю
- **THEN** ответ 404, перевод не создаётся

#### Scenario: Отклонение несуществующего или чужого целевого кошелька
- **WHEN** `POST /api/transfers` отправлен с `to_wallet_id`, которого нет ни у одного пользователя, либо
  принадлежащим другому пользователю
- **THEN** ответ 404, перевод не создаётся

#### Scenario: Отклонение неположительной суммы
- **WHEN** `POST /api/transfers` отправлен с `amount`, равным нулю или отрицательным
- **THEN** ответ 400 с ошибкой валидации, перевод не создаётся

#### Scenario: Отклонение суммы с превышением числа знаков валюты
- **WHEN** `POST /api/transfers` отправлен с `amount`, число знаков после запятой которого превышает
  `decimal_places` валюты `currency_id`
- **THEN** ответ 400, перевод не создаётся, сумма не округляется

#### Scenario: Отказ без аутентификации
- **WHEN** `POST /api/transfers` отправлен без действительного access-cookie
- **THEN** ответ 401, перевод не создаётся

### Requirement: Список переводов пользователя с фильтром по кошельку и пагинацией
`GET /api/transfers` SHALL возвращать постраничный список переводов, принадлежащих только текущему
аутентифицированному пользователю, отсортированный по `occurred_at` по убыванию, затем по `id` по убыванию как
детерминированному tie-breaker (новые переводы первыми). Опциональный query-параметр `wallet_id` SHALL сужать
список до переводов, у которых `wallet_id` совпадает с `from_wallet_id` ИЛИ с `to_wallet_id`. Опциональные
`date_from` и `date_to` (включительно, диапазон по `occurred_at`) SHALL дополнительно сужать список; если заданы
оба и `date_from` позже `date_to`, запрос SHALL быть отклонён. Параметры пагинации — `limit` (1..100, по умолчанию
20) и `offset` (≥ 0, по умолчанию 0).

#### Scenario: Список содержит только переводы текущего пользователя
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/transfers`, при этом в системе есть переводы,
  принадлежащие другим пользователям
- **THEN** ответ 200 содержит только переводы текущего пользователя, `total` равен числу его переводов

#### Scenario: Порядок списка — новые переводы первыми
- **WHEN** у пользователя есть несколько переводов с разными `occurred_at`
- **THEN** ответ 200 возвращает их отсортированными по `occurred_at` по убыванию, а при равном `occurred_at` — по
  `id` по убыванию

#### Scenario: Фильтр по кошельку учитывает и исходный, и целевой кошелёк
- **WHEN** пользователь запрашивает `GET /api/transfers?wallet_id=...` для одного из своих кошельков
- **THEN** ответ 200 содержит переводы, у которых указанный кошелёк является либо `from_wallet_id`, либо
  `to_wallet_id`

#### Scenario: Фильтр по диапазону дат
- **WHEN** пользователь запрашивает `GET /api/transfers?date_from=...&date_to=...`
- **THEN** ответ 200 содержит только переводы с `occurred_at` в указанном диапазоне включительно

#### Scenario: Некорректный диапазон дат отклоняется
- **WHEN** `GET /api/transfers?date_from=...&date_to=...` запрошен с `date_from`, позже `date_to`
- **THEN** ответ 400 с ошибкой валидации

#### Scenario: Пагинация по умолчанию
- **WHEN** `GET /api/transfers` запрошен без параметров `limit`/`offset`
- **THEN** ответ 200 использует `limit = 20`, `offset = 0`

#### Scenario: Недопустимые параметры пагинации отклоняются
- **WHEN** `GET /api/transfers` запрошен с `limit` вне диапазона 1..100 или с отрицательным `offset`
- **THEN** ответ 400 с ошибкой валидации

### Requirement: Чтение одного перевода
`GET /api/transfers/{transfer_id}` SHALL возвращать перевод по `id`, только если он принадлежит текущему
аутентифицированному пользователю.

#### Scenario: Успешное чтение своего перевода
- **WHEN** аутентифицированный пользователь запрашивает `GET /api/transfers/{transfer_id}` для своего перевода
- **THEN** ответ 200 содержит `id`, `from_wallet_id`, `to_wallet_id`, `currency_id`, `amount`, `occurred_at`,
  `created_at`, `updated_at`

#### Scenario: Несуществующий перевод
- **WHEN** запрашивается `GET /api/transfers/{transfer_id}` с `transfer_id`, которого нет ни у одного пользователя
- **THEN** ответ 404

### Requirement: Полное обновление перевода
`PUT /api/transfers/{transfer_id}` SHALL полностью заменять `from_wallet_id`, `to_wallet_id`, `currency_id`,
`amount` и `occurred_at` перевода, принадлежащего текущему аутентифицированному пользователю, с той же валидацией,
что и при создании. Частичное обновление (`PATCH`) не поддерживается.

#### Scenario: Успешная полная замена
- **WHEN** аутентифицированный пользователь отправляет `PUT /api/transfers/{transfer_id}` для своего перевода с
  новыми корректными `from_wallet_id`, `to_wallet_id`, `currency_id`, `amount` и `occurred_at`
- **THEN** ответ 200 содержит перевод с обновлёнными значениями и обновлённым `updated_at`

#### Scenario: Обновление несуществующего перевода
- **WHEN** `PUT /api/transfers/{transfer_id}` отправлен с `transfer_id`, которого нет ни у одного пользователя
- **THEN** ответ 404, изменения не применяются

#### Scenario: Обновление с той же валидацией входных данных, что и создание
- **WHEN** `PUT /api/transfers/{transfer_id}` отправлен с одинаковыми `from_wallet_id`/`to_wallet_id`, валютой, не
  входящей в набор валют одного из кошельков, неположительной суммой, суммой с превышением знаков валюты, либо
  несуществующим/чужим `from_wallet_id` или `to_wallet_id`
- **THEN** ответ 400 или 404 (в зависимости от причины), изменения не применяются

### Requirement: Удаление перевода
`DELETE /api/transfers/{transfer_id}` SHALL физически удалять перевод, принадлежащий текущему аутентифицированному
пользователю.

#### Scenario: Успешное удаление
- **WHEN** аутентифицированный пользователь отправляет `DELETE /api/transfers/{transfer_id}` для своего перевода
- **THEN** ответ 204, перевод удалён; последующий `GET /api/transfers/{transfer_id}` для того же `id` возвращает
  404

#### Scenario: Удаление несуществующего перевода
- **WHEN** `DELETE /api/transfers/{transfer_id}` отправлен с `transfer_id`, которого нет ни у одного пользователя
- **THEN** ответ 404

### Requirement: Изоляция данных по владельцу
Каждый эндпоинт, оперирующий конкретным переводом (`GET`, `PUT`, `DELETE /api/transfers/{transfer_id}`), SHALL
проверять принадлежность перевода текущему аутентифицированному пользователю на уровне запроса к данным (не
отдельной проверкой после чтения). Перевод, принадлежащий другому пользователю, MUST быть неотличим снаружи от
несуществующего: в обоих случаях SHALL возвращаться 404, а не 403.

#### Scenario: Чужой перевод недоступен для чтения
- **WHEN** пользователь A запрашивает `GET /api/transfers/{transfer_id}` с `transfer_id` перевода, принадлежащего
  пользователю B
- **THEN** ответ 404, а не 403; данные перевода B не раскрываются

#### Scenario: Чужой перевод недоступен для обновления
- **WHEN** пользователь A отправляет `PUT /api/transfers/{transfer_id}` с `transfer_id` перевода, принадлежащего
  пользователю B
- **THEN** ответ 404, перевод B не изменяется

#### Scenario: Чужой перевод недоступен для удаления
- **WHEN** пользователь A отправляет `DELETE /api/transfers/{transfer_id}` с `transfer_id` перевода,
  принадлежащего пользователю B
- **THEN** ответ 404, перевод B не удаляется

#### Scenario: Список одного пользователя не содержит переводов другого
- **WHEN** пользователь A запрашивает `GET /api/transfers`, при этом у пользователя B есть переводы по его
  собственным кошелькам
- **THEN** ответ 200 содержит только переводы пользователя A
