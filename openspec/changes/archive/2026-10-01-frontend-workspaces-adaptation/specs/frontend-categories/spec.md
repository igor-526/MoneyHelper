## MODIFIED Requirements

### Requirement: Маршрут и точка входа раздела «Категории»
Маршрут `/categories` SHALL быть доступен только авторизованному пользователю с выбранным текущим воркспейсом
(под `RequireAuth`, затем `RequireWorkspace`, тем же поддеревом маршрутов, что и остальные разделы приложения).
Раздел `navItems` SHALL НЕ содержать отдельный пункт для категорий — точкой входа SHALL быть ссылка со страницы
«Настройки» (`/settings`).

#### Scenario: Точка входа видна на странице «Настройки»
- **WHEN** авторизованный пользователь открывает страницу «Настройки»
- **THEN** на странице отображается блок «Категории» со ссылкой, ведущей на `/categories`

#### Scenario: Переход по прямой ссылке без авторизации
- **WHEN** неавторизованный пользователь переходит на `/categories`
- **THEN** приложение перенаправляет его на `/login`, страница категорий не отображается

#### Scenario: Нижняя панель навигации не содержит пункт «Категории»
- **WHEN** авторизованный пользователь просматривает навигацию приложения (нижнюю панель на телефоне, верхнее меню
  на широком экране)
- **THEN** среди пунктов навигации нет отдельного пункта, ведущего на `/categories`

### Requirement: Список категорий с фильтром по типу
Экран `/categories` SHALL загружать список категорий текущего воркспейса одним запросом
`GET /api/workspaces/{workspace_id}/categories` с максимально допустимым `limit` (100), без клиентской постраничной
подгрузки. Над списком SHALL отображаться переключатель фильтра по типу со значениями «Все», «Доход», «Расход»;
выбор фильтра, отличного от «Все», SHALL передаваться в запрос как query-параметр `type`. Каждая категория SHALL
отображаться карточкой: иконка, название, индикатор типа (доход/расход). Карточки SHALL отображаться в порядке, в
котором backend вернул список (без клиентской пересортировки).

#### Scenario: Загрузка списка
- **WHEN** экран `/categories` только что открыт
- **THEN** отображается индикатор загрузки, пока ответ `GET /api/workspaces/{workspace_id}/categories` не получен

#### Scenario: Список получен и не пуст
- **WHEN** `GET /api/workspaces/{workspace_id}/categories` вернул страницу с одной или несколькими категориями
- **THEN** каждая категория отображается карточкой с иконкой, названием и индикатором типа, в порядке ответа
  backend

#### Scenario: Пустой список
- **WHEN** `GET /api/workspaces/{workspace_id}/categories` вернул пустую страницу (в текущем воркспейсе ещё нет
  категорий, соответствующих текущему фильтру)
- **THEN** вместо списка карточек отображается пустое состояние с призывом создать категорию, переключатель
  фильтра остаётся видимым и доступным

#### Scenario: Фильтр меняет отображаемый набор
- **WHEN** пользователь переключает фильтр с «Все» на «Доход» (или «Расход»)
- **THEN** выполняется запрос `GET /api/workspaces/{workspace_id}/categories` с query-параметром `type`, равным
  выбранному значению, и список обновляется, отображая только категории этого типа

#### Scenario: Ошибка загрузки списка
- **WHEN** `GET /api/workspaces/{workspace_id}/categories` завершился ошибкой
- **THEN** пользователь получает уведомление об ошибке (toast) по общему правилу обработки ошибок API

### Requirement: Создание категории
Экран `/categories` SHALL позволять создать категорию в текущем воркспейсе через форму (тип, название, иконка),
открывающуюся поверх списка в `Drawer` на телефоне и в `Modal` на широком экране — без перехода на отдельный
маршрут. Форма SHALL требовать выбранный тип, непустое название и выбранную иконку. Успешное создание
(`POST /api/workspaces/{workspace_id}/categories`) SHALL добавить новую категорию в список без перезагрузки
страницы.

#### Scenario: Успешное создание категории дохода
- **WHEN** пользователь заполняет форму созданием категории с типом «Доход» корректными данными и отправляет её
- **THEN** запрос `POST /api/workspaces/{workspace_id}/categories` выполняется с `type: "income"`, форма
  закрывается, список категорий обновляется и содержит новую категорию, пользователь получает уведомление об
  успехе

#### Scenario: Успешное создание категории расхода
- **WHEN** пользователь заполняет форму созданием категории с типом «Расход» корректными данными и отправляет её
- **THEN** запрос `POST /api/workspaces/{workspace_id}/categories` выполняется с `type: "expense"`, форма
  закрывается, список категорий обновляется и содержит новую категорию, пользователь получает уведомление об
  успехе

#### Scenario: Ошибка валидации по полю при создании
- **WHEN** backend отвечает на `POST /api/workspaces/{workspace_id}/categories` ошибкой 400 с сообщениями по
  конкретным полям (`type`, `name`, `icon`)
- **THEN** форма остаётся открытой, соответствующие поля показывают полученные сообщения об ошибке, категория не
  добавляется в список

#### Scenario: Конфликт названия в пределах типа
- **WHEN** пользователь создаёт категорию с названием, уже занятым другой категорией того же типа в этом
  воркспейсе, и backend отвечает 409
- **THEN** форма остаётся открытой, ошибка отображается у поля «Название» (не общим уведомлением), категория не
  добавляется в список

#### Scenario: Одинаковое название в разных типах не конфликтует
- **WHEN** пользователь создаёт категорию с названием, уже занятым существующей категорией **другого** типа в
  этом воркспейсе
- **THEN** запрос `POST /api/workspaces/{workspace_id}/categories` выполняется успешно, новая категория
  добавляется в список

### Requirement: Редактирование категории
Экран `/categories` SHALL позволять отредактировать существующую категорию той же формой, что используется для
создания, предзаполненной текущими значениями выбранной категории из уже загруженного списка (без дополнительного
запроса). Успешное редактирование (`PUT /api/workspaces/{workspace_id}/categories/{id}`) SHALL обновить категорию
в списке без перезагрузки страницы.

#### Scenario: Открытие формы редактирования
- **WHEN** пользователь нажимает «Редактировать» на карточке категории
- **THEN** открывается та же форма, что и для создания, с полями, предзаполненными текущими типом, названием и
  иконкой этой категории

#### Scenario: Успешное редактирование
- **WHEN** пользователь изменяет данные в форме редактирования и отправляет её
- **THEN** запрос `PUT /api/workspaces/{workspace_id}/categories/{id}` выполняется, форма закрывается, карточка
  категории в списке отображает обновлённые данные, пользователь получает уведомление об успехе

#### Scenario: Конфликт названия при переименовании
- **WHEN** пользователь переименовывает категорию в название, уже занятое другой категорией того же типа в этом
  воркспейсе, и backend отвечает 409
- **THEN** форма остаётся открытой, ошибка отображается у поля «Название» (не общим уведомлением), категория в
  списке не изменяется

### Requirement: Удаление категории
Экран `/categories` SHALL позволять удалить категорию с карточки списка через подтверждение (`Popconfirm`), без
перехода на отдельный маршрут или экран подтверждения. Успешное удаление
(`DELETE /api/workspaces/{workspace_id}/categories/{id}`) SHALL убрать категорию из списка без перезагрузки
страницы. Если backend отклоняет удаление (409, у категории есть операции), пользователь SHALL увидеть понятное
сообщение из ответа backend по общему правилу обработки ошибок API, без дополнительной специальной обработки на
экране.

#### Scenario: Успешное удаление
- **WHEN** пользователь подтверждает удаление категории без связанных операций
- **THEN** запрос `DELETE /api/workspaces/{workspace_id}/categories/{id}` выполняется, категория пропадает из
  списка, пользователь получает уведомление об успехе

#### Scenario: Удаление отклонено из-за существующих операций
- **WHEN** пользователь подтверждает удаление категории, у которой есть операции, и backend отвечает 409
- **THEN** категория остаётся в списке, пользователь получает уведомление с сообщением из ответа backend
  (`detail`), объясняющим, что удаление невозможно из-за существующих операций

#### Scenario: Отмена удаления
- **WHEN** пользователь открывает подтверждение удаления и отменяет его
- **THEN** запрос `DELETE /api/workspaces/{workspace_id}/categories/{id}` не выполняется, категория остаётся в
  списке без изменений
