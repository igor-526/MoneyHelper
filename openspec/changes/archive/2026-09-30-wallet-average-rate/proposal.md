## Why

Кошелёк с несколькими валютами (например, Alipay в CNY и RUB) хранит остатки обеих валют одновременно; пополнение
(011) обязательно указывает суммы сразу во всех валютах, из чего можно вывести курс. Сейчас пользователь нигде не
видит, по какому эффективному курсу фактически «обходится» трата в одной из валют такого кошелька — приходится
считать вручную. Нужен производный, read-only курс кошелька между его валютами.

## What Changes

- Новый эндпоинт для получения среднего курса между валютами конкретного кошелька, выведенного из истории его
  собственных пополнений (та же формула, что уже применена в аналитике, 012: простое арифметическое среднее
  `target_leg.amount / source_leg.amount` по пополнениям с ногами в обеих валютах — только выборка сужена до
  одного кошелька вместо всех кошельков воркспейса за диапазон дат).
- Курс — за всю историю пополнений кошелька целиком, без обязательного диапазона дат (в отличие от 012, где
  диапазон обязателен, потому что отчёт явно про период; здесь нет понятия отчётного периода — есть один кошелёк
  и его собственная история).
- Валюта кошелька без единого подходящего пополнения — не имеет курса; такие валюты перечисляются отдельно в
  ответе, суммы/курс не подставляются искусственно (тот же принцип, что `unconverted_currencies` в 012).
- Никаких изменений в модели баланса, трат (010) или пополнений (011) — курс не влияет на то, как считается баланс
  кошелька, это чисто производное значение для отображения.

## Capabilities

### New Capabilities
(нет)

### Modified Capabilities
- `wallets`: добавляется новое требование — эндпоинт получения среднего курса между валютами кошелька.

## Impact

- **БД**: не затрагивается, миграция не требуется (только `SELECT` поверх уже существующих `transactions`/
  `transaction_legs`, тот же источник данных, что у аналитики и балансов).
- **API**: новый эндпоинт `GET /api/workspaces/{workspace_id}/wallets/{wallet_id}/rates` (точный путь и форма
  ответа фиксируются в design.md).
- **core/services**: новый сервис по образцу `BalanceService`/`AnalyticsService` — читает ноги пополнений кошелька
  через `TransactionRepository`, агрегирует курс в Python (тот же аргумент производительности, что уже принят в
  012 — датасет личного приложения мал).
- **Frontend**: не затрагивается этим изменением — отображение курса в UI является будущей отдельной задачей.
