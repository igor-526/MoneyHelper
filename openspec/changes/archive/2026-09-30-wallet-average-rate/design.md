## Context

Аналитика (012, `core/services/analytics.py`) уже умеет усреднять курс между парой валют по ногам пополнений:
`_average_rates` группирует `TopupLegRecord` (из `TransactionRepository.list_topup_legs_for_rates`) по
`transaction_id`, затем для каждой исходной валюты, для которой в той же транзакции есть нога и в целевой валюте,
берёт отношение сумм и усредняет простым средним. Это именно тот алгоритм, который нужен и здесь — разница только
в выборке пополнений (не «все кошельки воркспейса за диапазон дат», а «один конкретный кошелёк, за всю историю»).

## Goals / Non-Goals

**Goals:**
- Новый эндпоинт, возвращающий средний курс между валютами одного кошелька, выведенный из его собственных
  пополнений, без диапазона дат.
- Переиспользовать алгоритм усреднения из аналитики, а не копировать его.
- Валюты кошелька без единого подходящего пополнения — явно перечислены в ответе, не искажают остальные курсы.

**Non-Goals:**
- FIFO-партии/очерёдность расходования — рассмотрено и отклонено (см. [[wallet-average-rate-design]] в памяти
  сессии/`docs/tasks/021_wallet_average_rate.md`).
- Изменение модели баланса (010/011) — курс не влияет на то, как считается баланс.
- Frontend-отображение — отдельная будущая задача.
- Диапазон дат как параметр — сознательно не вводится (см. Decision 2).

## Decisions

### 1. Новый метод репозитория `list_topup_legs_for_wallet_rates`, а не расширение существующего

**Решение:** в `core/protocols/repositories/transaction_repository.py` добавляется
`list_topup_legs_for_wallet_rates(workspace_id: UUID, wallet_id: UUID) -> list[TopupLegRecord]` — фильтрует ноги
пополнений по `transactions.workspace_id == workspace_id AND transactions.wallet_id == wallet_id`, без диапазона
дат. Возвращаемый тип — существующий `TopupLegRecord` (`transaction_id`, `currency_id`, `amount`), без изменений
формы: `wallet_id` не нужен в самой записи, так как весь результат уже отфильтрован по одному кошельку на уровне
SQL. Тот же приём, что уже применён в `TransactionRepository` для `list_legs_for_analytics` и
`list_topup_legs_for_rates`, сосуществующих в одном широком протоколе ради разных потребителей (012, design.md,
Decision 7) — новый метод для нового потребителя, не расширение сигнатуры существующего.

**Отвергнутая альтернатива: добавить `wallet_id: UUID | None` и сделать `date_from`/`date_to` опциональными в
`list_topup_legs_for_rates`.** Отвергнута — раздула бы сигнатуру метода необязательными для части потребителей
параметрами (`AnalyticsService` никогда не передаёт `wallet_id`, новый сервис никогда не передаёт даты); отдельный
узкий метод читается яснее на месте вызова и не создаёт немых комбинаций параметров.

### 2. Без диапазона дат — курс за всю историю пополнений кошелька

**Решение:** эндпоинт не принимает `date_from`/`date_to`. Курс кошелька — не отчёт за период (как аналитика), а
характеристика самого кошелька на текущий момент; у пользователя нет естественного способа выбрать «период»,
глядя на одну трату, — только сам кошелёк и его накопленная история пополнений.

**Отвергнутая альтернатива: обязательный диапазон дат, как в 012.** Отвергнута — там диапазон обязателен, потому
что весь эндпоинт — это отчёт за явно выбранный период (значение курса иначе неопределено). Здесь такого отчёта
нет: один вызов должен просто отвечать «какой сейчас средний курс этого кошелька», без дополнительного решения
пользователя о периоде.

### 3. Чистая функция усреднения выносится и переиспользуется аналитикой

**Решение:** алгоритм из `AnalyticsService._average_rates` (группировка `TopupLegRecord` по `transaction_id`,
затем усреднение `target/source` по всем транзакциям, где есть нога в обеих валютах) выносится в чистую функцию
`average_rates(topup_legs: Sequence[TopupLegRecord], target_id: UUID, source_ids: set[UUID]) -> dict[UUID, Decimal]`
в `core/services/rate_averaging.py`. `AnalyticsService._average_rates` становится тонкой обёрткой: получает ноги
через `list_topup_legs_for_rates`, вызывает `average_rates`. Новый `WalletRateService` делает то же самое поверх
`list_topup_legs_for_wallet_rates`. Дублирования нетривиальной денежной математики в двух сервисах не остаётся.

**Отвергнутая альтернатива: скопировать логику в новый сервис.** Отвергнута — два места с одинаковой нетривиальной
арифметикой неизбежно разойдутся при будущих правках (например, если усреднение когда-то станет средневзвешенным).

### 4. Новый `WalletRateService`, а не метод на `WalletService`

**Решение:** `core/services/wallet_rate.py::WalletRateService(transactions: TransactionRepository, wallets:
WalletRepository)` — отдельный сервис, по образцу `BalanceService`/`AnalyticsService` (оба тоже отдельные сервисы
поверх данных, которыми управляют другие сервисы). `get_wallet_rates(wallet_id, workspace_id, *,
target_currency_id) -> WalletRates`:
1. `wallets.get_by_id(wallet_id, workspace_id)` — `None` → `NotFoundError` (тот же принцип «чужой/несуществующий
   кошелёк — 404», что и везде).
2. `target_currency_id` MUST быть в `wallet.currency_ids` — иначе `ClientError` (400), по аналогии с проверкой
   валюты операции в 010.
3. `source_ids = set(wallet.currency_ids) - {target_currency_id}`; если пусто (кошелёк с одной валютой) —
   возвращается пустой результат, без ошибки.
4. Ноги через `list_topup_legs_for_wallet_rates`, курсы — через `average_rates`.
5. `unrated_currency_ids = sorted(source_ids - rates.keys(), key=str)`.

**Отвергнутая альтернатива: метод `WalletService.get_rates(...)`.** Отвергнута — `WalletService` отвечает за CRUD
кошелька (единственная ответственность, S из SOLID); курс — отдельный сценарий чтения поверх данных из другой
сущности (`transactions`), как балансы и аналитика уже вынесены из `WalletService`/`TransactionService` в свои
сервисы.

### 5. Путь и форма ответа

**Решение:** `GET /api/workspaces/{workspace_id}/wallets/{wallet_id}/rates?target_currency_id=<uuid>` — вложенный
ресурс кошелька, по прямому образцу `GET .../wallets/{wallet_id}/balances` (011/020). `target_currency_id` —
обязательный query-параметр (без параметра неясно, для какой валюты считать курс при кошельке с более чем двумя
валютами). Ответ:
```json
{
  "target_currency_id": "...",
  "rates": [{"currency_id": "...", "rate": "12.8205128205"}],
  "unrated_currency_ids": ["..."]
}
```
`rates` — по одной записи на каждую валюту кошелька (кроме целевой), для которой нашёлся хотя бы один
подходящий топ-ап; `unrated_currency_ids` — остальные валюты кошелька без подходящего топ-апа (аналог
`unconverted_currencies` из 012, здесь без искусственной подстановки курса `1`).

**Отвергнутая альтернатива: поле в ответе `GET .../wallets/{wallet_id}/balances`.** Отвергнута — курс требует
обязательного параметра (`target_currency_id`), а баланс — нет; смешивание опционально-параметризованного курса в
безусловный ответ баланса усложнило бы оба контракта. Отдельный эндпоинт яснее и не меняет уже стабильный ответ
балансов.

### 6. Новый схемный тип `Rate` — тот же паттерн сериализации, что `Money`, но без привязки к `decimal_places` валюты

**Решение:** `core/schemas/rate.py::Rate = Annotated[Decimal, Field(max_digits=28, decimal_places=10,
allow_inf_nan=False), PlainSerializer(..., return_type=str, when_used="json")]` — курс не является суммой в
конкретной валюте (у него нет `decimal_places` валюты, к которому привязываться, как у `Money`), поэтому получает
собственный тип с фиксированной точностью 10 знаков после запятой. Сервис округляет вычисленный курс до 10 знаков
(`ROUND_HALF_UP`, тот же режим округления, что уже принят в 012) один раз, на выходе — до того как отдать в схему.

**Отвергнутая альтернатива: переиспользовать `Money`.** Отвергнута — `Money` — про суммы денег в конкретной
валюте (8 знаков, 24 цифры); курс — безразмерное отношение, использование `Money` для него смешивало бы два
разных домена одним типом ради экономии кода.

## Risks / Trade-offs

- [Новый эндпоинт читает те же строки `transaction_legs`, что уже читают балансы/аналитика — лишний путь чтения
  тех же данных] → незначительно при личном объёме данных, тот же аргумент производительности, что уже принят в
  008–012.
- [10 знаков после запятой у `Rate` — произвольный выбор, может оказаться недостаточным для валют с очень разным
  номиналом] → минимальный риск: с текущим набором валют (CNY/RUB/USDT, `decimal_places` 2 или 6) курсы такого
  масштаба, что 10 знаков — большой запас; при необходимости меняется в одном месте (`core/schemas/rate.py`).

## Migration Plan

1. `core/services/rate_averaging.py` — чистая функция `average_rates`, unit-тесты (перенос покрытия из тестов
   `AnalyticsService._average_rates`, если оно там было отдельным, плюс новые случаи).
2. Рефакторинг `AnalyticsService._average_rates` на использование `average_rates` — существующие тесты аналитики
   обязаны остаться зелёными без изменений (чистый рефакторинг, не смена поведения).
3. `core/protocols/repositories/transaction_repository.py` — новый метод `list_topup_legs_for_wallet_rates`;
   `repositories/transaction.py` — реализация; `tests/fakes/transaction_repository.py` — реализация для тестов.
4. `core/schemas/rate.py` — тип `Rate`.
5. `core/services/wallet_rate.py::WalletRateService` + unit-тесты на fake-репозиториях (несколько валют, валюта
   без пополнений, кошелёк с одной валютой, `target_currency_id` не из валют кошелька, чужой/несуществующий
   кошелёк).
6. `depends/wallet_rate.py`, `api/wallet_rates.py` (роутер под `/api/workspaces/{workspace_id}/wallets/{wallet_id}
   /rates`, `Depends(require_workspace)`) + smoke-тест.
7. QualityGate (`make format`, `make lint`, `make test`); миграция БД не требуется, `make test-infra` — по
   необходимости, если появятся SQL-специфичные сценарии (агрегация по нескольким транзакциям), иначе unit/smoke
   достаточно (тот же уровень покрытия, что у 012, которая тоже не требовала новых `test-infra` сценариев).
