## Context

`Transaction` (010, дополнена в 011) — одна сущность и для обычных операций (одна нога), и для пополнений
(несколько ног); `TransactionRepository.add`/`update` и API уже прокидывают её поля насквозь через все слои
(`core/entities` → `models`/`repositories` → `core/schemas`/`api/schemas`). Комментарий добавляется как ещё одно
такое поле — без нового протокола, сервиса или эндпоинта.

## Goals / Non-Goals

**Goals:**
- Необязательный текстовый комментарий на операции, включая пополнения, читаемый и изменяемый через уже
  существующие эндпоинты.
- Явная нормализация пустого/пробельного ввода в `null`, тот же приём, что уже применён к `name` в 008/009/020.
- Разумный явный лимит длины, задокументированный с обоснованием (нет точного прецедента в проекте).

**Non-Goals:**
- Комментарии к переводам (`transfers`) — отдельная сущность, не запрошена пользователем.
- Форматирование (markdown), вложения, история правок комментария — только обычный текст, текущее значение.
- Поиск/фильтрация операций по тексту комментария — не запрошено.
- Отображение в UI — отдельная будущая задача (023).

## Decisions

### 1. Максимальная длина — 1000 символов

**Решение:** `comment: str | None`, `max_length=1000` на уровне схемы API, `String(1000)` в БД (тот же явный
бандинг типа, что у остальных текстовых полей проекта — `String(100)` у `name` кошельков/категорий/воркспейсов, не
`Text`).

**Обоснование.** В проекте нет точного прецедента поля именно такой природы (свободная заметка, не короткое имя).
1000 символов — это несколько предложений, достаточно для контекста покупки («серый рюкзак Anta, подарок
племяннику»), но не позволяет превратить операцию в документ; тот же порядок величины, что у типичного лимита
комментария в потребительских финансовых приложениях.

**Отвергнутая альтернатива: `Text` без ограничения длины.** Отвергнута — проект нигде не использует неограниченный
текст; явная граница проще для UI (счётчик символов, `textarea` фиксированной высоты) и для БД (предсказуемый
размер строки).

### 2. Нормализация — strip + пустая строка → `null`, на уровне схемы API

**Решение:** `field_validator` в `TransactionCreate`/`TopupCreate` (тот же приём, что `strip_name` в
`api/schemas/{wallet,category,workspace}.py`): если после `strip()` строка пустая — возвращается `None`, а не
ошибка валидации (в отличие от `name`, комментарий необязателен, поэтому пустой ввод — это «без комментария», а
не ошибка).

**Отвергнутая альтернатива: нормализация в `core/services/transaction.py`.** Отвергнута — во всём проекте strip-
нормализация текстовых полей уже живёт в `api/schemas/*` (валидация формы ввода — обязанность схемы, не бизнес-
сервиса); согласованность с существующим местом важнее теоретической переносимости на другой транспорт.

### 3. `comment` — сквозное поле без нового протокола/сервиса

**Решение:** добавляется в `core/entities/transaction.py::Transaction` (`comment: str | None = None`), в
`models/transaction.py::transactions` (`Column("comment", String(1000), nullable=True)`), в
`repositories/transaction.py` (`_map_row`, `add`, `update` — план ниже), в `core/protocols/repositories/
transaction_repository.py::TransactionRepository.update` (новый именованный параметр `comment: str | None`),
`tests/fakes/transaction_repository.py` — аналогично, в `TransactionService.create_transaction`/`create_topup`/
`update_transaction` (новый параметр, прокидывается в конструктор `Transaction`/в `repositories.update`), в
`api/schemas/transaction.py` (`TransactionCreate`/`TopupCreate`/`TransactionOut`), в `api/transactions.py`
(передача `body.comment` в вызовы сервиса). Никакого нового файла-сущности или отдельного эндпоинта не появляется
— комментарий не самостоятельная сущность, а атрибут операции.

**Отвергнутая альтернатива: отдельная таблица `transaction_comments` (1:1 или история версий).** Отвергнута —
задача явно про «свободный текстовый комментарий» (одно текущее значение), не про историю правок; отдельная
таблица добавила бы JOIN на каждое чтение операции ради несуществующей сейчас потребности.

## Risks / Trade-offs

- [Комментарий виден в ответе API уже сейчас, до готовности frontend (023)] → не риск: поле необязательно,
  существующий (пока несовместимый по путям, см. 020) frontend всё равно не читает и не пишет его; когда
  frontend адаптируется, поле уже будет готово.
- [1000 символов — произвольный выбор] → минимальный риск, меняется в одном месте (`api/schemas/transaction.py`,
  `models/transaction.py` + миграция) при необходимости пересмотра.

## Migration Plan

1. `core/entities/transaction.py` — поле `comment: str | None = None`.
2. `models/transaction.py` — колонка `comment` (`String(1000)`, `nullable=True`); `make be-makemigrations
   msg="transaction_comments"`, `make be-migrate` (чистое добавление колонки, без ручных правок миграции и без
   очистки данных — в отличие от 020).
3. `core/protocols/repositories/transaction_repository.py::update` — параметр `comment: str | None`;
   `repositories/transaction.py` (`_map_row`, `add`, `update`) и `tests/fakes/transaction_repository.py` —
   реализация.
4. `core/services/transaction.py` — `create_transaction`/`create_topup`/`update_transaction` принимают и
   прокидывают `comment`.
5. `api/schemas/transaction.py` — `comment` в `TransactionCreate`, `TopupCreate` (со strip-нормализацией),
   `TransactionOut`; `api/transactions.py` — передача `body.comment` в сервис.
6. Unit-тесты сервиса (нормализация уже произошла на уровне схемы, сервис просто хранит/возвращает значение —
   тесты проверяют сквозной проход через create/update/get/list), smoke-тесты API (пустой/пробельный комментарий →
   `null` в ответе, обычный текст сохраняется, слишком длинный `comment` → 400, пополнение с комментарием, `PUT`
   меняет комментарий).
7. QualityGate (`make format`, `make lint`, `make test`); `make test-infra` — не обязателен (чистое добавление
   колонки без новой бизнес-логики на уровне SQL), но прогоняется для подтверждения, что ничего не сломано.
