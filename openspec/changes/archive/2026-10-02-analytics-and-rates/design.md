## Context

После 024–028: воркспейс имеет валюту `W`, кошелёк — одну валюту `C`. Пополнение (`/topups`, категория `income`)
содержит ноги `{W, C}` (одна нога, если `W == C`); расход (`/transactions`) — одну ногу в `C`; переводы (отдельная
таблица) в аналитику и курс не входят. Аналитика (012) остаётся «по умолчанию мультивалютной»: читает все ноги всех
операций, `display_currency` обязателен, курс — среднее `target/source` по операциям с числом ног больше одной.
`GET .../rates` отдаёт заглушку. Алгоритм `average_rates(topup_legs, target_id, source_ids)` рабочий и
переиспользуется.

## Goals / Non-Goals

**Goals:**
- Суммы аналитики по умолчанию в валюте воркспейса; курс усредняется по пополнениям за диапазон анализа.
- Курс кошелька считается по его пополнениям, не смешивается между кошельками и воркспейсами.
- Пополнения для курса определяются типом категории, а не числом ног.

**Non-Goals:**
- Внешние источники курсов, FIFO, frontend (035), изменения схемы БД.

## Decisions

1. **`display_currency` остаётся, но необязателен.** Имя параметра не меняется (меньше поломок контракта; ответ по
   прежнему содержит `display_currency_id`). По умолчанию — валюта воркспейса. Допустимые значения — валюта
   воркспейса и валюты кошельков воркспейса; любое другое значение (в т. ч. существующая валюта справочника, не
   связанная с воркспейсом) — 400, потому что курса для третьей валюты не существует. Ответ 400 при неизвестной
   валюте сохраняется (одно сообщение на оба случая: «Недопустимая валюта отображения»). Альтернатива «убрать
   параметр совсем» отвергнута: отчёт в валюте кошелька (например «сколько я потратил в CNY») полезен и достижим на
   тех же данных — пополнение содержит обе ноги, поэтому курс `W -> C` есть.

2. **Одна нога на операцию — в валюте кошелька.** Репозиторий `list_legs_for_analytics` по-прежнему отдаёт все
   ноги; сервис оставляет только ноги, чья валюта равна валюте кошелька операции. Для расхода это его единственная
   нога; для пополнения — нога в `C` (нога в `W` при `W != C` дублирует ту же сумму в валюте воркспейса и без этого
   правила удвоила бы доход). Бизнес-правило находится в сервисе, а не в SQL; репозиторий и его fake остаются
   неизменными по конструктору. Валюты кошельков сервис получает через новый узкий протокол
   `WalletCurrencyReader.get_currency_ids(workspace_id) -> dict[UUID, UUID]` (wallet_id -> currency_id) — один
   запрос на воркспейс; протокол реализуют SQL- и in-memory-репозитории кошельков (ISP, по образцу
   `WorkspaceCurrencyReader`). Фильтр `currency_id` аналитики — это валюта кошелька (валюта оставшейся ноги);
   `group_by=currency` группирует по валюте кошелька.

3. **Курс для аналитики — по валюте, а не по кошельку.** Для каждой валюты ноги `X != display` берётся среднее
   `display_leg / X_leg` (простое среднее, как в 012) по пополнениям воркспейса за `[date_from, date_to]`, у которых
   есть ноги в обеих валютах. Благодаря тому, что пополнение хранит обе ноги, для `display = W` курс есть у каждой
   валюты кошелька с пополнениями за диапазон, а для `display = C` — у `W` (в этом случае расходы кошельков валюты
   `W` пересчитываются в `C`); пара двух разных валют кошельков (`C1 -> C2`) курса не имеет и остаётся в
   `unconverted_currencies` (по условию задачи «валюта без пополнений за диапазон остаётся в
   `unconverted_currency_ids`»; в API имя поля прежнее — `unconverted_currencies`). Фильтры аналитики не сужают
   набор пополнений для курса. Альтернатива «курс по кошельку» отвергнута для аналитики: отчёт агрегирует кошельки,
   а курс — свойство пары валют воркспейса; per-wallet курс доступен в `GET .../rates`.

4. **Пополнения определяются типом категории.** `TransactionRepository.list_topup_legs_for_rates(workspace_id, *,
   wallet_id, date_from, date_to)` возвращает ноги операций с категорией `income`; `wallet_id`, `date_from`,
   `date_to` необязательны (`None` — без ограничения). Условие «число ног > 1» удалено. Пополнения с одной ногой
   (валюты совпали) отбираются, но курс из них не извлекается — `average_rates` пропускает транзакции без
   пары ног. Fake-репозиторий ведёт себя так же (LSP).

5. **Контракт `GET .../wallets/{wallet_id}/rates`.** Без query-параметров. Ответ:
   `{"workspace_currency_id": UUID, "wallet_currency_id": UUID, "rate": "…" | null}`. `rate` — сколько единиц
   валюты воркспейса стоит одна единица валюты кошелька (`W_leg / C_leg`), простое среднее по пополнениям этого
   кошелька за всю историю (диапазон не задаётся); квантуется до 10 знаков (`Rate`). Если валюты совпадают,
   `rate = "1"` без обращения к пополнениям. Если пополнений с обеими ногами нет — `rate = null` (признак «нет
   курса»; 200, не ошибка). Чужой/несуществующий кошелёк — 404. Расчёт в `WalletRateService` (зависимости:
   `WalletRepository`, `WorkspaceCurrencyReader`, `TransactionRepository`), алгоритм — `average_rates`.
   Альтернатива «список курсов `rates[]`» отвергнута: пара всегда одна.

6. **Контракт аналитики (итог).** Запрос: `date_from`, `date_to` (обязательны), `group_by` (`wallet|category|
   currency`), `display_currency` (необязателен), `wallet_id`, `category_id`, `currency_id`, `type`. Ответ:
   `{display_currency_id, buckets[{group_key, income, expense}], unconverted_currencies[UUID]}` — форма не
   меняется.

7. **Миграций нет.**

## Risks / Trade-offs

- Доход пополнения в `W` считается как сумма в `C`, умноженная на средний курс диапазона, а не по точной ноге `W`
  (курс среднее простое) → расхождение с реально введённой суммой; принято по решению пользователя «курс всегда
  средний за диапазон».
- Контракты `GET .../rates` и поведение аналитики пополнений меняются; frontend несовместим до 035 (по плану после
  backend).
- Сервис аналитики делает ещё два запроса (валюта воркспейса, валюты кошельков) — незначительная нагрузка.
