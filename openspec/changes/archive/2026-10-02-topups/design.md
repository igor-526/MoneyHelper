## Context

После `workspace-currency` и `wallet-single-currency` у воркспейса есть основная валюта, у кошелька — одна валюта.
В 025 сделана временная адаптация: пополнение (`POST .../transactions/topups`) принимает ровно одну ногу в валюте
кошелька. Тип операции (доход/расход) определяется типом категории; отдельного поля «вид операции» в БД нет, а
пополнение отличается от обычной операции только числом ног. Задача 026 делает пополнение самостоятельным ресурсом
с правильным правилом ног; расходы (027), переводы (028) и курс (029) — вне рамок.

## Goals / Non-Goals

**Goals:**
- Отдельный ресурс пополнений с полным CRUD.
- Правило ног `{валюта воркспейса, валюта кошелька}` как стратегия за протоколом.
- Раздельные списки пополнений и расходов.

**Non-Goals:**
- Новая схема БД, расчёт среднего курса и аналитика (029), расходы (027), frontend.

## Decisions

1. **Форма эндпоинтов: отдельный ресурс `/api/workspaces/{workspace_id}/topups`**, а не подресурс
   `/transactions/topups`. Открытый вопрос задачи решён так, потому что у пополнения свой жизненный цикл (чтение,
   список, `PUT`, `DELETE`), свой набор полей и своя вкладка в UI; подресурс потребовал бы либо дублировать
   `/{transaction_id}`, либо оставить пополнения в общем списке операций. Эндпоинты:
   `POST /topups` (201), `GET /topups` (список), `GET /topups/{topup_id}`, `PUT /topups/{topup_id}`,
   `DELETE /topups/{topup_id}` (204). Старый `POST /transactions/topups` удаляется (без совместимости: frontend
   до 033 всё равно несовместим). Коллизии статического `/topups` с `/{transaction_id}` больше нет.

2. **Раздельные списки без нового поля в БД.** Вид операции выводится из типа категории: пополнение — операция с
   категорией `income`, расход — с `expense`. Поскольку создание «просто дохода» удаляется, а `POST`/`PUT
   /transactions` отклоняют `income`, множества не пересекаются. Отдельной колонки `kind` не вводим: она
   дублировала бы тип категории и могла бы разойтись с ним (расхождение при смене типа категории; тип категории
   редактируется через `PUT`). Альтернатива (колонка `kind` + миграция) отвергнута как избыточная для 026.
   - `GET /topups` вызывает репозиторий с `type=income`; `GET /transactions` — с `type=expense`, параметр `type`
     из запроса списка расходов удаляется.
   - `GET/PUT/DELETE /transactions/{id}` для пополнения и `.../topups/{id}` для расхода дают 404: общий помощник
     `core/services/transaction_kind.py::get_of_type` читает операцию и категорию и возвращает `None` при
     несовпадении типа. Репозиторий операций не меняется (SRP, без новых методов в протоколе).

3. **Правило набора ног — стратегия за протоколом `TopupLegsRule`** (`core/protocols/topup_legs_rule.py`):
   `applies(workspace_currency_id, wallet_currency_id) -> bool` и
   `required_currency_ids(workspace_currency_id, wallet_currency_id) -> frozenset[UUID]`. Реализации в
   `core/services/topup_legs.py`: `SameCurrencyTopupLegs` (валюты совпали → `{валюта}`),
   `CrossCurrencyTopupLegs` (разные → обе). `TopupService` получает `Sequence[TopupLegsRule]`, берёт первое
   подходящее правило и сверяет набор валют ног (принцип O: новый вариант — новая реализация, без `if`).
   Регистрация правил — в `depends/topup.py`. Пустой набор ног, отсутствующая или лишняя валюта, повтор валюты — 400
   (сообщения перечисляют коды валют, как раньше).

4. **Валюта воркспейса.** Сервис знает только `workspace_id` (авторизация воркспейса — `require_workspace`), а
   `WorkspaceRepository.get_by_id` требует `user_id`. Добавлен узкий протокол
   `WorkspaceCurrencyReader.get_currency_id(workspace_id) -> UUID | None` (ISP, по образцу `WalletCounter`); его
   реализуют SQL- и in-memory-репозитории воркспейсов. Если воркспейс не найден, сервис отдаёт 404 (в обычном потоке
   недостижимо, воркспейс уже проверен зависимостью).

5. **Схемы.** `api/schemas/topup.py`: `TopupLegIn`, `TopupCreate` (`wallet_id`, `category_id`, `legs`,
   `occurred_at`, `comment`; `legs` — непустой список, `Money gt=0`), `TopupUpdate = TopupCreate` (полная замена,
   все поля кроме `occurred_at`/`comment` обязательны), `TopupOut` (форма как у операции: `legs` отсортированы по
   коду валюты), `TopupListParams` (`wallet_id`, `category_id`, `date_from`, `date_to` + пагинация; параметра `type`
   нет). `TransactionLegIn`/`TopupCreate` удаляются из `api/schemas/transaction.py`.

6. **Сервисы (SOLID).** `TopupService` (`core/services/topup.py`) — сценарии пополнений; `TransactionService`
   перестаёт знать про пополнения (удаляется `create_topup` и проверка набора ног). Оба используют
   `get_of_type`. Зависимости сервиса пополнений: `TransactionRepository`, `WalletRepository`,
   `CategoryRepository`, `CurrencyRepository`, `WorkspaceCurrencyReader`, правила ног, `Clock`, `IdGenerator`.
   Проверка ноги (положительность, существование валюты, точность по `decimal_places`) вынесена в общую функцию
   `core/services/money_validation.py::validate_leg_amount`, которой пользуются `TopupService` и `TransactionService`.

7. **Баланс и аналитика не меняются.** `balance_delta` считает ноги в валюте кошелька; нога в валюте воркспейса при
   разных валютах в баланс кошелька не попадает. Аналитика читает ноги всех операций (в т.ч. пополнений) как раньше;
   её переделка и вклад пополнений в курс — задача 029 (`list_topup_legs_for_rates` по «числу ног > 1» остаётся
   до неё).

8. **Миграций нет.** Данные пополнений хранятся в тех же таблицах.

## Risks / Trade-offs

- Вид операции выводится из типа категории: смена типа категории с `income` на `expense` перекинула бы пополнение
  в расходы. → Это поведение уже допустимо в проекте для операций (тип категории с операциями меняется свободно);
  при необходимости запретить смену типа категории с операциями — отдельное изменение (категории), не 026.
- Контракт `/transactions` и `/transactions/topups` ломается; frontend несовместим до 031–035 (по плану после
  backend).
- Гонка «изменили валюту кошелька/воркспейса параллельно с пополнением» невозможна: валюта кошелька не меняется при
  наличии операций (025), валюта воркспейса — при наличии кошельков (024).
