## Context

Сейчас каждая пользовательская сущность (`wallets`, `categories`, `transactions`/`transaction_legs`, `transfers`)
хранит прямую колонку `user_id` и изолируется по ней: каждый репозиторий фильтрует `entity_id AND user_id` в одном
запросе (`WalletRepository.get_by_id`, `CategoryRepository`, `TransactionRepository`, аналогично для `transfers`).
Балансы (`BalanceService`) и аналитика (`AnalyticsService`) агрегируют поверх этих же данных, тоже по `user_id`.

Нужно ввести промежуточный уровень владения: рабочее пространство (`workspace`), принадлежащее одному
пользователю, — и переместить на него ту роль, которую сейчас играет `user_id` у перечисленных сущностей.
Изоляция между воркспейсами одного пользователя должна быть такой же полной, как сейчас между пользователями
(подтверждено пользователем в постановке задачи, [[docs/tasks/020_workspaces.md]]).

## Goals / Non-Goals

**Goals:**
- Новая сущность `workspaces`, CRUD `/api/workspaces*`, принадлежит пользователю (`user_id`), без совместного
  доступа.
- `wallets`, `categories`, `transactions` (включая пополнения), `transfers` изолируются по `workspace_id` вместо
  `user_id`; тот же паттерн одного запроса `entity_id AND workspace_id`, что и сейчас с `user_id`.
- Балансы и аналитика scoped по воркспейсу: курс усредняется только по пополнениям того же воркспейса, список
  операций/переводов — только того же воркспейса.
- Существующие REST-пути переносятся под `/api/workspaces/{workspace_id}/...`; принадлежность воркспейса текущему
  пользователю проверяется один раз на уровне общей зависимости, а не в каждом сервисе отдельно.
- Миграция Alembic: новая таблица, новые колонки, старые тестовые данные не переносятся (очищаются).

**Non-Goals:**
- Совместный доступ нескольких пользователей к одному воркспейсу, роли, приглашения.
- Frontend (переключатель воркспейса, экран управления, адаптация существующих экранов под новые пути) —
  отдельная будущая задача.
- Перенос/миграция существующих данных в дефолтный воркспейс — решено пользователем не делать (реальных
  пользователей ещё нет).
- Автосоздание воркспейса «по умолчанию» при регистрации — не запрашивалось; пустое состояние «нет ни одного
  воркспейса» с призывом создать первый — тот же принцип онбординга, что уже принят для кошельков/категорий/
  операций (`docs/tasks/002_roadmap.md`), просто на уровень выше.

## Decisions

### 1. `workspace_id` заменяет `user_id` на сущностях, а не добавляется рядом с ним

**Решение:** колонка `user_id` удаляется из `wallets`, `categories`, `transactions`, `transfers`; вместо неё
добавляется `workspace_id` (UUID, `ForeignKey("workspaces.id", ondelete="CASCADE")`, `nullable=False`). Владение
пользователем восстанавливается транзитивно через `workspaces.user_id`. Во всех протоколах/сервисах/репозиториях
этих сущностей параметр `user_id: UUID` переименовывается в `workspace_id: UUID` — чистое переименование, та же
позиция и семантика (`WHERE entity_id = ... AND workspace_id = ...` вместо `AND user_id = ...`), без изменения
формы методов.

**Отвергнутая альтернатива: хранить оба поля (`user_id` и `workspace_id`).** Отвергнута — два источника правды об
одном и том же факте владения неизбежно могут разойтись (например, при ручной правке БД или будущем баге), и
пришлось бы решать, какое поле весит больше при проверке; хранить только `workspace_id` и получать пользователя
через `workspaces.user_id` при необходимости — единственный источник правды.

### 2. Проверка принадлежности воркспейса — общая зависимость `require_workspace`, REST-пути вложенные

**Решение:** путь `workspace_id` передаётся как часть URL, ресурсы вложены:
`/api/workspaces/{workspace_id}/wallets`, `/api/workspaces/{workspace_id}/categories`,
`/api/workspaces/{workspace_id}/transactions` (и `/transactions/topups`), `/api/workspaces/{workspace_id}/transfers`,
`/api/workspaces/{workspace_id}/wallets/{wallet_id}/balances`, `/api/workspaces/{workspace_id}/analytics` — прямое
продолжение уже принятого в 011 паттерна вложенного ресурса (`GET /api/wallets/{wallet_id}/balances`). Новая
зависимость `depends/workspace.py::require_workspace(workspace_id: UUID, user_id: UUID = Depends(get_current_user),
workspaces: WorkspaceRepository = Depends(get_workspace_repository)) -> UUID` проверяет `workspaces.get_by_id
(workspace_id, user_id) is not None` (иначе `NotFoundError`, 404 — не 403, тот же принцип, что и у чужого кошелька/
категории) и возвращает валидированный `workspace_id`. Каждый роутер сущностей объявляет
`workspace_id: Annotated[UUID, Depends(require_workspace)]` вместо текущего
`user_id: Annotated[UUID, Depends(get_current_user)]` и передаёт его в сервис на той же позиции. FastAPI связывает
путь-параметр `workspace_id` из префикса роутера с одноимённым параметром в `require_workspace` по имени — тот же
механизм, что уже используется для `wallet_id` в `GET /api/wallets/{wallet_id}/balances`.

**Отвергнутая альтернатива: заголовок/query-параметр `X-Workspace-Id`.** Отвергнута — путь более RESTful, согласуется
с уже принятым прецедентом вложенного ресурса (011) и не требует отдельной документации нестандартного заголовка;
ошибка невалидного/чужого воркспейса остаётся обычным 404 при разборе пути, а не отдельным кодом ошибки авторизации.

**Отвергнутая альтернатива: «текущий воркспейс» как поле в JWT/cookie (серверная сессия).** Отвергнута — токены
и так уже не хранятся на сервере (`AGENTS.md`, «Авторизация»), а смена текущего воркспейса потребовала бы либо
перевыпуска токена на каждое переключение, либо отдельного мутируемого состояния — сложнее, чем явный путь.

### 3. Удаление воркспейса — каскадное, без проверки на непустоту

**Решение:** `workspace_id` на `wallets`/`categories`/`transactions`/`transfers` — `ON DELETE CASCADE`. `DELETE
/api/workspaces/{workspace_id}` физически удаляет воркспейс и всё, что в нём есть, одним запросом, без
предварительной проверки на существование дочерних записей (в отличие от `DELETE /api/wallets/{id}`, который
отклоняется 409 при наличии операций).

**Обоснование.** Удаление кошелька/категории — точечное действие внутри продолжающегося набора данных, поэтому
блокировка при наличии зависимых операций защищает от случайной потери истории. Удаление воркспейса — осознанное
«стереть весь этот контекст целиком» (например, поездка закончилась и данные больше не нужны); требовать сначала
вручную удалить все кошельки/категории/операции внутри обесценивало бы саму пользу воркспейса как единицы удаления.

**Отвергнутая альтернатива: `RESTRICT`, как у кошелька/категории с операциями.** Отвергнута по обоснованию выше —
заставила бы пользователя вручную очищать воркспейс перед удалением, что прямо противоречит цели фичи.

### 4. `workspaces` — новая top-level сущность по образцу `wallets`/`categories`

**Решение:** таблица `workspaces` (`id`, `user_id` — `ForeignKey("users.id", ondelete="CASCADE")`, `name` —
`String(100)`, `created_at`, `updated_at`), без `icon` (не запрашивалось) и без уникальности имени в пределах
пользователя (нет заявленной потребности — как и у `wallets`, где имена не уникальны; в отличие от `categories`,
где уникальность обоснована конкретным сценарием дублей). Сортировка списка — `created_at ASC, id ASC`, как у
`wallets`/`categories` (не `occurred_at DESC`, как у `transactions`). CRUD, слои и файлы — по прямому образцу
`wallets` (008): `core/entities/workspace.py`, `core/protocols/repositories/workspace_repository.py`,
`core/services/workspace.py`, `models/workspace.py`, `repositories/workspace.py`, `core/schemas/workspace.py`,
`api/workspaces.py`, `depends/workspace.py`. Валидация названия — непустая строка после `strip()`, тот же паттерн,
что у названия кошелька/категории.

### 5. Миграция — очистка существующих данных перед добавлением `NOT NULL workspace_id`

**Решение:** одна миграция Alembic: (1) создать `workspaces`; (2) `TRUNCATE wallets, categories, transactions,
transfers CASCADE` (каскадно очищает и зависимые `transaction_legs`, `wallet_currencies` через существующие
`ON DELETE CASCADE`) — по решению пользователя старые тестовые данные не переносятся; (3) добавить колонку
`workspace_id` (`NOT NULL`, FK `ondelete="CASCADE"`) на `wallets`, `categories`, `transactions`, `transfers`; (4)
удалить колонку `user_id` и её FK/индексы с этих же таблиц; (5) пересоздать `UniqueConstraint` категорий как
`(workspace_id, type, name)` вместо `(user_id, type, name)`. Порядок (сначала очистка, потом `NOT NULL` без
`server_default`) исключает необходимость бэкофилла.

**Отвергнутая альтернатива: бэкофилл — создать по одному дефолтному воркспейсу на пользователя и перенести туда
существующие строки.** Отвергнута явным решением пользователя («можно всё сбросить») — усложнение ради данных,
которые и так тестовые и создавались только для проверки PWA (019).

## Risks / Trade-offs

- [`TRUNCATE ... CASCADE` необратимо удаляет все существующие кошельки/категории/операции/переводы] → осознанно,
  по решению пользователя; данные тестовые, реальных пользователей нет.
- [Переименование `user_id → workspace_id` затрагивает почти все методы протоколов/сервисов/репозиториев `wallets`,
  `categories`, `transactions`, `transfers`, `balances`, `analytics` — большой, но механический диф] → снижается
  тем, что это **чистое** переименование параметра без изменения контракта метода; тесты на fake-репозиториях
  (`tests/fakes/`) ловят рассинхронизацию сигнатур на этапе тестирования, а не в проде.
- [Frontend продолжит ходить по старым `/api/wallets`, `/api/categories` и т. д. путям и сразу сломается после
  этого изменения] → осознанный breaking change API, зафиксированный в proposal.md; адаптация frontend — отдельная
  следующая задача, а не часть этого изменения (аналогично тому, как в 003–012 backend разрабатывался раньше
  frontend-экранов).
- [`require_workspace` — новая зависимость, дублирующая часть смысла `get_current_user`] → минимальный риск: она
  тонкая (одна проверка `get_by_id`), переиспользует `WorkspaceRepository`, а не дублирует логику авторизации.

## Migration Plan

1. `core/entities/workspace.py`, `core/protocols/repositories/workspace_repository.py`,
   `core/services/workspace.py` + unit-тесты на fake-репозитории.
2. `models/workspace.py` (регистрация в `models/__init__.py`), `repositories/workspace.py`.
3. `core/schemas/workspace.py`, `api/workspaces.py`, `depends/workspace.py` (включая `require_workspace`) + smoke-тест.
4. Миграция Alembic (`make be-makemigrations msg="workspaces"`, ручной обзор — очистка данных пишется вручную,
   `--autogenerate` её не сгенерирует).
5. Переименование `user_id → workspace_id` и смена путей поэтапно по сущностям: `wallets` → `categories` →
   `transactions`(+`topups`) → `transfers` → `balances` → `analytics`; после каждой — прогон её существующих
   unit/smoke/infrastructure тестов с обновлёнными фикстурами (создание воркспейса вместо/наряду с пользователем).
6. `make test-infra`: новый набор сценариев изоляции между воркспейсами одного пользователя (по образцу уже
   существующих сценариев изоляции между пользователями) для каждой из пяти сущностей/агрегатов.
7. Полный QualityGate (`make format`, `make lint`, `make test`, `make test-infra`).
