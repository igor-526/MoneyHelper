## Why

Пользователь ведёт финансы нескольких независимых контекстов (например, разных поездок) в одном аккаунте. Сейчас
все кошельки, категории, операции и переводы принадлежат напрямую пользователю и показываются одним общим
списком — данные разных поездок неизбежно смешиваются (общий список кошельков, общие категории, общий баланс и
общая аналитика). Нужна полная изоляция между независимыми рабочими пространствами одного пользователя, по образцу
уже существующей изоляции между разными пользователями.

## What Changes

- Новая сущность `workspaces`: рабочее пространство принадлежит одному пользователю (без совместного доступа,
  ролей и приглашений); CRUD (`/api/workspaces*`).
- **BREAKING**: `wallets`, `categories`, `transactions` (включая пополнения), `transfers` и производные от них
  (`balances`, `analytics`) переходят с прямой изоляции по `user_id` на изоляцию по `workspace_id`. Существующие
  эндпоинты этих сущностей переносятся под путь, явно указывающий воркспейс
  (`/api/workspaces/{workspace_id}/wallets` и т. п. — точная форма фиксируется в design.md).
- Категории перестают быть общими для пользователя — список категорий отдельный в каждом воркспейсе, симметрично
  кошелькам/операциям/переводам.
- Курс в балансах/аналитике (усреднение по ногам пополнений) считается только по пополнениям того же воркспейса.
- Миграция Alembic добавляет таблицу `workspaces` и `workspace_id` на существующих таблицах; существующие
  тестовые данные (кошельки/категории/операции/переводы) не переносятся в дефолтный воркспейс — реальных
  пользователей ещё нет, миграция вправе их очистить.
- Frontend (переключатель воркспейса, экран управления воркспейсами, адаптация существующих экранов под новые
  пути API) — вне рамок этого изменения, отдельная будущая задача.

## Capabilities

### New Capabilities
- `workspaces`: CRUD рабочих пространств пользователя (создание, список, переименование, удаление), полная
  изоляция между воркспейсами одного пользователя и между пользователями.

### Modified Capabilities
- `wallets`: изоляция и адресация — с `user_id` на `workspace_id`; пути под `/api/workspaces/{workspace_id}/...`.
- `categories`: то же самое; список категорий больше не общий для пользователя, а отдельный на воркспейс.
- `transactions`: то же самое (включая пополнения с несколькими ногами).
- `transfers`: то же самое.
- `analytics`: усреднение курса и выборка операций scoped по воркспейсу, а не по всем данным пользователя.

## Impact

- **БД**: новая таблица `workspaces` (владелец, название); новая колонка `workspace_id` (NOT NULL, FK) на
  `wallets`, `categories`, `transactions`, `transfers`; миграция Alembic очищает существующие данные этих таблиц
  перед добавлением NOT NULL колонки (тестовые данные, реальных пользователей нет).
- **API**: новый роутер `/api/workspaces*`; существующие роутеры `wallets`, `categories`, `transactions`,
  `transfers`, `balances`, `analytics` меняют путь и схему изоляции (владелец проверяется через `workspace_id` +
  принадлежность воркспейса текущему пользователю, а не напрямую через `user_id` на каждой сущности).
- **core/repositories**: репозитории соответствующих сущностей меняют фильтр изоляции; появляется
  `WorkspaceRepository`/`WorkspaceService` по образцу существующих (`WalletRepository` и т. п.).
- **Frontend**: не затрагивается этим изменением (см. «Вне рамок» задачи 020); существующие экраны продолжат
  ходить по старым путям API до отдельной frontend-задачи — это осознанный breaking change API, фиксируемый только
  на backend.
