## Context

После `wallet-single-currency` (025) у кошелька `currency_id`. Там же сделана временная адаптация переводов:
`currency_id` по-прежнему передаётся в запросе, хранится в `transfers.currency_id` и должен совпадать с валютой обоих
кошельков (одно сообщение об ошибке для всех несовпадений). `BalanceContributor.balance_delta(wallet_id, workspace_id,
currency_id)` уже возвращает одно число; перевод фильтрует себя по `transfers.currency_id`. Средний курс (`WalletRateService`)
переводов не читает. Остаётся: вывести валюту из кошельков, зафиксировать судьбу колонки, дать отдельное правило и
сообщение для «разных валют».

## Goals / Non-Goals

**Goals:**
- Перевод только между кошельками одной валюты; валюта не передаётся и не может разойтись с кошельками.
- Баланс обоих кошельков корректен; перевод не влияет на курс.

**Non-Goals:**
- Конвертация при переводе, аналитика/курс (029), frontend (034).

## Decisions

1. **Колонка `transfers.currency_id` удаляется.** Валюта перевода — производная от кошельков, поэтому её хранение —
   денормализация, способная разойтись с ними. Инвариант не нарушается после создания: валюту кошелька нельзя менять
   при наличии переводов (025, `WalletUsageChecker`), а удалить кошелёк с переводами нельзя (`ON DELETE RESTRICT`).
   Следствия: `Transfer` без `currency_id`; `TransferOut` без `currency_id` — клиент берёт валюту из любого из двух
   кошельков (`from_wallet_id`); JOIN на каждом чтении не добавляется (лишняя сложность ради поля, выводимого клиентом).

2. **Миграция `20261002_0012`.** `TRUNCATE transfers` (явная ревьюемая очистка, как в 0008/0010/0011: по решению
   024–025 данные валютной модели не переносятся) и `DROP COLUMN currency_id`. `downgrade`: возвращает `currency_id`
   (nullable), заполняет её валютой кошелька-отправителя, затем `NOT NULL` + FK на `currencies` (`ON DELETE RESTRICT`).

3. **Валидация в `TransferService`.** Порядок: отправитель ≠ получатель → оба кошелька найдены в воркспейсе (404) →
   `from_wallet.currency_id == to_wallet.currency_id` (иначе `ClientError` «Перевод возможен только между кошельками
   одной валюты») → сумма положительна → точность суммы по валюте кошельков (валюта читается из `CurrencyRepository`).
   Проверка валюты кошельков вынесена в приватный метод; создание и обновление используют один путь.

4. **Схемы.** `TransferCreate` получает `extra="forbid"`: переданный `currency_id` отклоняется (400), а не молча
   теряется (по образцу `WalletCreate`). `TransferUpdate = TransferCreate`.

5. **Баланс.** Контракт `BalanceContributor.balance_delta(wallet_id, workspace_id, currency_id)` общий для всех
   источников и не меняется; `TransferRepository.balance_delta` принимает `currency_id` согласно протоколу, но не
   фильтрует по нему: любой перевод кошелька по инварианту в валюте этого кошелька. Знак — `+` для получателя,
   `−` для отправителя; ветвления по виду операции нет.

6. **Курс.** Перевод не участвует в среднем курсе: `WalletRateService` не зависит от `TransferRepository`
   (закреплено требованием спеки и тестом). Источник курса — пополнения (026/029).

## Risks / Trade-offs

- Контракт API переводов ломается; frontend не совместим до 034 (по плану идёт после backend).
- Клиенту приходится выводить валюту перевода из кошелька — осознанная цена отсутствия денормализации.
