## Why

Кошельки (задача 008) и категории (задача 009) хранят иконку как строку — имя иконки Lucide. Обеим будущим задачам
нужен единый переиспользуемый способ проверить на входе API, что это имя входит в согласованный набор, и единый
источник правды для этого набора, общий с frontend (иначе backend и frontend разойдутся в том, какие имена
допустимы, и пользователь увидит запасную иконку вместо ожидаемой). Задача 007 закрывает эту потребность заранее,
не дожидаясь 008/009, — по аналогии с тем, как задача 006 подготовила справочник валют до того, как он понадобился
кошелькам.

## What Changes

- Реестр допустимых имён иконок `backend/src/core/icons.json` — отсортированный список строк в kebab-case,
  единственный источник правды для backend и frontend. Стартовый набор — 23 уже существующих бизнес-иконки категорий
  и кошельков из `frontend/src/shared/ui/icons.ts` (еда, транспорт, зарплата и т. п.); расширение набора в будущем —
  обычная правка JSON, не требует менять механизм.
- `backend/src/core/icons.py` — читает `icons.json` при импорте модуля и строит `ALLOWED_ICONS: frozenset[str]` и
  функцию `list_icon_names()` (отсортированный список для API).
- `backend/src/core/schemas/icon.py` — переиспользуемый Pydantic-тип `IconName` (аннотированная строка, проверяемая
  по `ALLOWED_ICONS`), по аналогии с `Money` (`core/schemas/money.py`). Предназначен для будущих схем кошельков и
  категорий (008/009); в этой задаче используется только для собственного unit-теста валидатора — подключать его
  пока не к чему.
- Эндпоинт `GET /api/icons` — без авторизации (справочник не персональные данные), возвращает отсортированный список
  имён без пагинации (список маленький и статический, `Page`/`PageParams` здесь не нужны).
- Frontend: `frontend/src/shared/ui/icons.ts` разделяется на `BUSINESS_ICONS` (набор, синхронизированный с
  `icons.json`) и `UI_ICONS` (иконки интерфейса — settings, sun, moon, log-out, download, share, wifi-off, не
  относящиеся к категориям/кошелькам, вне рамок iconpack); `ICONS` остаётся их объединением, поведение
  `Icon`/`resolveIcon` не меняется.
- Frontend-тест синхронизации: `vitest`-тест читает `backend/src/core/icons.json` напрямую с диска и сверяет его
  содержимое (без учёта порядка) с ключами `BUSINESS_ICONS` — это и есть правило синхронизации из задачи 007.
  Иконка получается frontend не сетевым запросом (там остаётся статическая карта имя → React-компонент, как того
  требует PWA precache/tree-shaking), а именно этим тестом.
- Unit-тесты backend (`ALLOWED_ICONS`/`list_icon_names`, валидатор `IconName`) и smoke-тест (`GET /api/icons`
  зарегистрирован и отвечает без БД).

Затрагивается API: новый эндпоинт `GET /api/icons`. **БД не затрагивается**: реестр — статический in-memory
справочник в коде (JSON-файл в `core`), не таблица; миграция Alembic не требуется. Frontend не получает список по
сети — только через тест синхронизации на этапе `vitest`. **BREAKING**-изменений нет.

## Impact

- `backend/src`: `core/icons.json` (данные), `core/icons.py` (`ALLOWED_ICONS`, `list_icon_names`),
  `core/schemas/icon.py` (`IconName`), `api/icons.py` (роутер `GET /api/icons`), `main.py` (подключение роутера).
  Ни `models/`, ни `repositories/`, ни `depends/`, ни миграций Alembic — статический реестр не требует ни одного из
  этих слоёв (нет персистентной сущности, нечего репозиторию читать/писать).
- Тесты backend: unit (`core/icons.py`, `core/schemas/icon.py`), smoke (`GET /api/icons` зарегистрирован и отвечает
  без БД, дополнение к списку эндпоинтов в существующем smoke-тесте).
- `frontend/src`: `shared/ui/icons.ts` (разделение на `BUSINESS_ICONS`/`UI_ICONS`), новый тест синхронизации
  (`shared/ui/icons.sync.test.ts` или аналогичное имя) на чтение `backend/src/core/icons.json` с диска.
  `shared/ui/Icon.tsx` и его тесты не меняются (поведение `resolveIcon`/`Icon` то же самое).

## Non-goals

- Загрузка пользовательских иконок (кастомные SVG/изображения) — вне рамок, реестр закрытый и курируемый.
- Сами кошельки и категории, которые будут использовать `IconName` в своих схемах, — задачи 008 и 009.
- Изменение версии `lucide-react` на frontend — версия уже зафиксирована (`^1.48.0`, `frontend/package.json`),
  отдельного решения не требуется.
- Полный набор иконок Lucide (>1000 штук) — реестр остаётся ограниченным курируемым подмножеством.
