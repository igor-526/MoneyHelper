## ADDED Requirements

### Requirement: Формат источника сидирования
Источник сидирования SHALL быть JSON-файлом в `src/seeds/`, содержащим список объектов, каждый из которых
однозначно соответствует одной записи целевой таблицы и MUST включать явный `id` (UUID), сгенерированный заранее
(`uuid.uuid4()`) и зафиксированный навсегда — выдуманные или изменяемые при каждом запуске идентификаторы
запрещены.

#### Scenario: Идентификатор — ключ сопоставления
- **WHEN** механизм сидирования обрабатывает объект из JSON-источника
- **THEN** он использует поле `id` этого объекта как ключ, по которому определяется, создавать новую запись или
  обновлять существующую

### Requirement: Идемпотентность повторного запуска
Повторный запуск сидирования с тем же источником SHALL приводить к тому же состоянию данных, что и первый запуск:
не создавать дублирующихся записей и не изменять уже совпадающие значения полей.

#### Scenario: Повторный запуск без изменений источника
- **WHEN** сидирование запускается дважды подряд с одним и тем же JSON-источником
- **THEN** после второго запуска число записей и значения их полей совпадают с состоянием после первого запуска

### Requirement: Обновление изменённой записи по идентификатору
Сидирование SHALL обновлять поля записи с существующим `id`, если запись с этим `id` присутствует в источнике с
изменёнными значениями остальных полей, не создавая новую запись и не меняя сам `id`.

#### Scenario: Изменилось название валюты
- **WHEN** в источнике для валюты с уже существующим в БД `id` изменилось поле `name`, а сидирование запускается
  повторно
- **THEN** запись с этим `id` в БД получает новое значение `name`; число записей в таблице не увеличивается

### Requirement: Отсутствие удаления при отсутствии записи в источнике
Сидирование MUST NOT удалять запись из БД, если запись, ранее созданная сидированием, отсутствует в источнике при
очередном запуске (её `id` убрали из JSON).

#### Scenario: Запись убрали из источника
- **WHEN** запись с определённым `id` есть в БД (создана предыдущим запуском сидирования), но отсутствует в
  текущем содержимом JSON-источника, и сидирование запускается снова
- **THEN** запись с этим `id` остаётся в БД без изменений

### Requirement: Безопасность при параллельном старте нескольких реплик
Сидирование на реальной БД SHALL получать эксклюзивную блокировку (PostgreSQL advisory lock) на время своей работы,
чтобы параллельный запуск сидирования из нескольких одновременно стартующих реплик приложения не приводил к гонке
условий (двойной вставке или частично применённому обновлению). Вторая и последующие реплики SHALL дождаться
завершения сидирования, держащего блокировку, а не завершиться с ошибкой из-за занятой блокировки.

#### Scenario: Блокировка удерживается другим процессом
- **WHEN** одно соединение удерживает advisory lock с ключом сидирования, и в это время другой процесс пытается
  начать сидирование с тем же ключом
- **THEN** второй процесс ожидает освобождения блокировки, а не завершается ошибкой и не начинает сидирование
  параллельно с первым

#### Scenario: Блокировка снимается после завершения
- **WHEN** сидирование завершается (успешно или с ошибкой)
- **THEN** удерживаемая им advisory lock освобождается, и следующий запрос блокировки с тем же ключом немедленно
  выполняется

### Requirement: Включение и отключение сидирования настройкой
Выполнение сидирования при старте приложения SHALL управляться настройкой окружения, читаемой через `Settings`, а
не проверкой окружения "на глаз" внутри кода запуска. При выключенной настройке приложение MUST NOT обращаться к
БД для сидирования при старте.

#### Scenario: Сидирование выключено
- **WHEN** настройка сидирования выключена, и приложение поднимается (включая жизненный цикл `lifespan`)
- **THEN** приложение стартует, не выполняя ни одного запроса к БД для сидирования

#### Scenario: Сидирование включено по умолчанию
- **WHEN** настройка сидирования не задана явно в окружении
- **THEN** сидирование выполняется при старте приложения (значение по умолчанию — включено)
