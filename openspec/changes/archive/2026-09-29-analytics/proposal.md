## Why

Пользователь ведёт доходы и расходы (010, `transactions`) и пополнения/переводы (011, `transfers`) в нескольких
кошельках и валютах, но не может посмотреть сводную картину: сколько заработано и потрачено за период, в разрезе
кошелька, категории или валюты, в единой валюте отображения. Задача 012 (финальный этап дорожной карты) закрывает
этот пробел — единственный read-эндпоинт аналитики, пересчитывающий суммы операций в валюту отображения по курсу,
выведенному из уже существующих данных (ног многовалютных пополнений, 011), без внешних источников курса.

## What Changes

- Новая капабилити `analytics` — `GET /api/analytics`: обязательные `display_currency` (валюта отображения),
  `date_from`/`date_to` (диапазон анализа), `group_by` (`wallet`/`category`/`currency`); опциональные фильтры
  `wallet_id`/`category_id`/`currency_id`/`type`, сужающие набор операций так же, как у `GET /api/transactions`.
  Ответ — суммы `income`/`expense` по корзинам выбранной оси группировки, в валюте отображения, плюс
  `unconverted_currencies` — валюты, для которых не нашлось курса в диапазоне.
- Курс между парой валют, отличных от валюты отображения, вычисляется как простое среднее арифметическое курсов
  `target_leg.amount / source_leg.amount` по всем операциям-пополнениям пользователя (>1 ноги на операцию) за тот
  же диапазон `date_from`/`date_to`, содержащим ногу в обеих валютах пары. Если операция уже в валюте отображения —
  курс тривиально `1`, поход за курсом не нужен.
- Если для пары валют в диапазоне нет ни одного пополнения с обеими валютами — суммы в этой валюте исключаются
  из итоговых сумм (не подставляется курс `1`, не возвращается ошибка на весь запрос); валюта попадает в
  `unconverted_currencies`.
- Суммируются неокруглённые конвертированные суммы (полная точность `Decimal`); округление до `decimal_places`
  валюты отображения происходит один раз — над уже просуммированным итогом по каждой корзине.
- Три оси группировки (`wallet`/`category`/`currency`) реализованы как стратегии за общим протоколом
  `AnalyticsDimension`, выбираемые по строковому `group_by` через реестр (`dict[str, AnalyticsDimension]`), а не
  через `if/elif` — открытость для добавления новых осей без правки существующего кода.
- Два новых read-метода `TransactionRepository` (без изменения схемы БД, без миграции): плоская выборка ног
  операций для основной агрегации (`list_legs_for_analytics`) и плоская выборка ног операций-пополнений для
  усреднения курса (`list_topup_legs_for_rates`).
- Вся арифметика курса/конвертации/группировки — в новом `AnalyticsService` на Python (двухфазный расчёт плохо
  ложится на декларативный SQL), тестируемом на fake-репозитории без БД.

## Capabilities

### New Capabilities
- `analytics`: единственный эндпоинт `GET /api/analytics`, возвращающий суммы доходов/расходов пользователя по
  выбранному срезу (кошелёк/категория/валюта) за явный диапазон дат, пересчитанные в валюту отображения по
  среднему курсу диапазона, выведенному из ног пополнений; изоляция данных и курса по владельцу.

### Modified Capabilities
_(нет — `transactions`/`transfers`/`wallets` не меняют публикуемое поведение; добавляются только новые read-методы
`TransactionRepository`, не описанные существующими спецификациями как контракт API)_

## Impact

- **БД**: не затрагивается — миграция Alembic не требуется. Новые read-методы `TransactionRepository` — обычные
  `SELECT` по уже существующим таблицам `transactions`/`transaction_legs`/`categories`.
- **API**: новый эндпоинт `GET /api/analytics` (роутер `api/analytics.py`, тег `Analytics`), под
  `Depends(get_current_user)`.
- **backend/src**: новый `core/protocols/analytics_dimension.py` (`AnalyticsDimension`, `WalletDimension`,
  `CategoryDimension`, `CurrencyDimension`); новый `core/services/analytics.py` (`LegRecord`, `AnalyticsService`);
  `core/protocols/repositories/transaction_repository.py` (два новых метода протокола); `repositories/transaction.py`
  (реализация новых методов); новый `api/schemas/analytics.py` (`AnalyticsQueryParams`, `AnalyticsBucketOut`,
  `AnalyticsOut`); новый `api/analytics.py`; новый `depends/analytics.py`; `main.py` (подключение роутера).
- Тесты backend: unit (`core/services/analytics.py` — усреднение курса, конвертация, группировка по трём осям,
  исключение неконвертируемых валют, округление, изоляция по владельцу), fake-репозиторий
  (`tests/fakes/transaction_repository.py` — реализация новых методов протокола), api (`tests/api/test_analytics.py`),
  smoke (регистрация нового пути), infrastructure (`tests/infrastructure/test_transaction_repository.py` —
  оба новых SQL-запроса на реальной БД).
- Frontend не затрагивается — задача 012 закрывает только backend (графики, экспорт — вне рамок и отдельная задача).

## Non-goals

- Внешние источники курсов валют — единственный источник курса в системе — ноги пополнений (011); не меняется
  этой задачей.
- Графики и экспорт аналитики — frontend-задачи, вне рамок.
- Произвольная гранулярность периода как ось группировки — «период» реализован как обязательный фильтр
  `date_from`/`date_to`, не как отдельная ось с бакетами (день/неделя/месяц), которую задача не специфицирует.
- Zero-fill пустых корзин — кошельки/категории/валюты без единой операции в диапазоне не включаются в ответ
  нулевой строкой (открытое множество, в отличие от фиксированного набора валют кошелька в балансе 011).
- Переводы (`transfers`, 011) — не участвуют в аналитике доходов/расходов: перевод не доход и не расход и не имеет
  категории, включение исказило бы категорийный/типовой срез.
- Редактирование/создание операций — эндпоинт только на чтение.
