## Context

После `workspace-currency` у воркспейса есть основная валюта. Кошелёк пока связан с набором валют через
`wallet_currencies`; на этом наборе завязаны операции, пополнения, переводы, баланс и средний курс кошелька.
Задачи 026–029 переделают правила операций и аналитики, поэтому здесь нужна только минимальная совместимая адаптация.

## Goals / Non-Goals

**Goals:**
- Инвариант «у кошелька ровно одна валюта» в сущности, БД, API.
- Запрет смены валюты кошелька с операциями/переводами.
- Все зависимые места backend работают и покрыты тестами.

**Non-Goals:**
- Новые правила пополнений/расходов/переводов, аналитика, frontend.

## Decisions

1. **Таблица.** `wallets.currency_id UUID NOT NULL REFERENCES currencies(id) ON DELETE RESTRICT`; `wallet_currencies`
   удаляется. Валюту справочника нельзя удалить, пока на неё ссылается кошелёк.

2. **Миграция `20261002_0011`.** Схема + явная ревьюемая очистка (исключение из «только схема», как в 0008/0010;
   решение пользователя — переносить нечего): `TRUNCATE wallets, transactions, transfers CASCADE`, затем
   удаление `wallet_currencies`, добавление `currency_id` сразу `NOT NULL` + FK (таблица пуста). `downgrade`:
   пересоздаёт `wallet_currencies`, переносит в неё `wallets.currency_id`, удаляет столбец (кошельки сохраняются).

3. **Смена валюты.** `PUT` — полная замена `name`, `icon`, `currency_id`. Если `currency_id` отличается от текущего
   и по кошельку есть операции или переводы — `ConflictError` (409, «ресурс используется», как при удалении).
   Совпадающая валюта не проверяется (переименование свободно). Новая валюта должна существовать (400).
   Проверка использования — узкий протокол `WalletUsageChecker.references_wallet(wallet_id)` (ISP/OCP: по образцу
   `BalanceContributor` сервис получает последовательность проверяющих; реализуют `TransactionRepository` и
   `TransferRepository`; новые источники ссылок подключаются без правки сервиса). Метод с тем же именем уже есть
   в fake-репозиториях как тестовый помощник — он становится реализацией протокола.

4. **Схемы.** `WalletCreate.currency_id: UUID`; `WalletUpdate = WalletCreate`. Pydantic по умолчанию молча игнорирует
   лишние поля, поэтому `WalletCreate` получает `extra="forbid"`: список `currency_ids` в запросе отклоняется (400), а
   не теряется. Запрос без `currency_id` — тоже 400.

5. **Форма ответа баланса.** `GET .../balances` — один объект `{currency_id, balance}` (не список из одного
   элемента): баланс по определению одно число в валюте кошелька, список закрепил бы устаревшую многовалютность.
   Путь не меняется. `BalanceService.get_wallet_balance` возвращает `(currency_id, Decimal)`.
   `BalanceContributor.balance_delta(wallet_id, workspace_id, currency_id) -> Decimal`: вклад считается только по
   ногам/переводам в валюте кошелька — это безопасно и для будущих пополнений 026 (нога в валюте воркспейса не
   попадёт в баланс кошелька).

6. **Минимальная совместимая адаптация (до 026–029).**
   - Обычная операция (`POST/PUT /transactions`): `currency_id` MUST равняться `wallet.currency_id` (иначе 400).
   - Пополнение (`POST /transactions/topups`): набор валют ног MUST равняться `{wallet.currency_id}`, т.е. ровно одна
     нога в валюте кошелька. Двухножное пополнение «валюта воркспейса + валюта кошелька» — задача 026.
   - Перевод: `currency_id` MUST равняться валюте обоих кошельков (общей валютой стала валюта кошелька; жёсткое
     правило «одна валюта у обоих кошельков» с отдельным сообщением — задача 028).
   - Средний курс (`GET .../rates`): `target_currency_id` MUST равняться валюте кошелька (иначе 400), ответ всегда
     пустой (`rates=[]`, `unrated_currency_ids=[]`) — источников курса у одновалютного кошелька нет. Эндпоинт
     и форма ответа сохраняются, `WalletRateService` теряет зависимость от `TransactionRepository`; настоящая
     переделка — задача 029.
   - Аналитика не затрагивается: она читает ноги операций и не использует `wallet.currency_ids`.

7. **Слои (SOLID).** `Wallet.currency_id` в сущности; `WalletService` получает `Sequence[WalletUsageChecker]`;
   SQL только в репозиториях (`references_wallet` в `repositories/transaction.py` и `transfer.py`); сборка в
   `depends/wallet.py`. Разделение `WalletRepository` на Reader/Writer не делалось: потребители (операции,
   переводы, баланс, курс) используют только `get_by_id`, сервис кошельков — всё; выделять сейчас — лишний
   рефакторинг, вернёмся, если в 026–029 потребуется (обоснованное отклонение от «`WalletReader`/`WalletWriter`»
   из текста задачи).

## Risks / Trade-offs

- Данные кошельков и операций теряются при миграции → осознанное решение пользователя, зафиксировано в миграции.
- Контракт API кошелька и баланса ломается; frontend не совместим до задач 031–035 (по плану они идут после backend).
- Гонка «создали операцию параллельно со сменой валюты кошелька» → допустима для личного приложения.
