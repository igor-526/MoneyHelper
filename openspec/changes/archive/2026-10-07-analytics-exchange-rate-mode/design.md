## Context

Текущая аналитика возвращает корзины доходов и расходов, а общий алгоритм `average_rates` вычисляет одно среднее
значение по пополнениям. Для временного графика этого недостаточно: ногам, читаемым для курса, требуется дата
операции, а API должен сохранить отдельную ответственность и не смешивать разные формы ответа. После активного
изменения `simplify-operations-and-analytics` `occurred_at` является наивным локальным временем, поэтому дата точки
берётся напрямую без параметра timezone.

Режим использует только собственные фактические пополнения воркспейса. RUB — фиксированная валюта котировки, одна
выбранная валюта — базовая. Схема данных уже содержит все необходимые сведения.

## Goals / Non-Goals

**Goals:**

- предоставить изолированный по пользователю и воркспейсу API дневной истории прямого курса к RUB;
- переиспользовать общий диапазон дат аналитики, включая состояние «Весь период»;
- показать на mobile-first графике одну плавную линию и точные исходные значения;
- показать под графиком min, max и avg по тем же дневным точкам;
- сохранить decimal-арифметику и слоистую SOLID-архитектуру.

**Non-Goals:**

- хранение котировок, внешние провайдеры, кросс-курсы и заполнение пропущенных дней;
- сравнение валют, свечи, прогноз и статистическое взвешивание;
- изменение существующего алгоритма пересчёта расходов или среднего курса кошелька.

## Decisions

### 1. Отдельный endpoint истории

Добавляется `GET /api/workspaces/{workspace_id}/analytics/rates`, а существующий `GET .../analytics` не получает
новый `group_by`. Формы данных различаются принципиально: обычная аналитика возвращает income/expense-корзины и
неконвертированные валюты, история — базовую/котируемую валюты и точки date/rate. Отдельный endpoint сохраняет
единственную ответственность схем и сервиса и не вводит union-ответ, зависящий от режима.

Альтернатива — `group_by=rate` в существующем endpoint — отклонена: она требует условной валидации параметров и
разных response shape в одном контракте.

### 2. Узкий сервис и протокол чтения курса

В `core` вводятся `ExchangeRateHistoryService`, сущность датированной ноги пополнения и узкий
`ExchangeRateHistoryReader`. Сервис зависит также от узких readers валют, валюты воркспейса и валют кошельков.
Composition root в `depends/` связывает их с SQLAlchemy-репозиториями. HTTP-роутер только валидирует query и
преобразует результат в response schema.

SQL остаётся в `repositories/transaction.py`: запрос читает только доходные транзакции указанного `workspace_id`,
их `occurred_at`, `transaction_id`, `currency_id` и `amount`, применяя необязательные границы. Репозиторий не
вычисляет бизнес-курс. Это позволяет fake-реализации соблюдать тот же протокол и проверять сервис без БД.

Альтернатива — расширить общий `TransactionRepository` ещё одним методом — отклонена для сервиса-потребителя:
узкий read-протокол не заставляет его зависеть от полного CRUD.

### 3. Прямая дневная котировка

Сервис группирует ноги сначала по транзакции, оставляет транзакции с обеими валютами и вычисляет
`RUB amount / base amount`. Затем образцы группируются по `date(occurred_at)` и усредняются простым средним. Это
согласуется с существующей невзвешенной формулой курса. Округление выполняется один раз для дневного результата до
десяти знаков типа `Rate`; JSON содержит decimal-строки.

Дни без образцов отсутствуют. Перенос последнего значения и интерполяция отклонены, потому что они создавали бы
курсы, которых пользователь не вводил. `type="monotone"` у Recharts влияет только на геометрию линии между
фактическими точками.

### 4. Допустимые валюты и фиксированный RUB

RUB находится через справочник по стабильному коду, а не через зашитый UUID. Базовой может быть нерублёвая основная
валюта воркспейса или валюта его кошелька. Это покрывает обе допустимые стороны пары пополнения и не позволяет
использовать endpoint как произвольный просмотр глобального справочника. Неизвестная, RUB или не связанная с
воркспейсом базовая валюта даёт 400; чужой/несуществующий воркспейс — 404.

Frontend строит тот же список из уже загруженных workspace, wallets и currencies, удаляет RUB и дубли, сортирует по
коду и выбирает первый вариант. Backend остаётся источником истины валидации.

### 5. Агрегаты вычисляются из отображаемых точек на frontend

Чистая функция получает decimal-строки `points` и возвращает min, max и среднее дневных значений. Среднее считается
по дням, а не повторно по исходным пополнениям, поэтому блок описывает ровно видимый график. Используется уже
принятый в аналитике decimal-подход без преобразования сумм в JavaScript `number`; округление — `ROUND_HALF_UP` до
десяти знаков.

Серверные агрегаты отклонены: они дублировали бы производные от небольшого массива ответа и усложняли контракт.

### 6. UI и ошибки

`RateMode` добавляется строкой в `ANALYTICS_MODES`; общие `DateRangeFilter` и подпись периода остаются на уровне
страницы. Новый TanStack Query hook зависит от `ApiClient`, включает workspace, currency и range в query key и
использует глобальную обработку всех классов ошибок. График помещается в `ResponsiveContainer`; selector и блок
агрегатов проектируются от ширины 320 px и не создают горизонтальную прокрутку.

## Risks / Trade-offs

- [Редкие пополнения дают разреженную линию] → показывать только честные точки и явное пустое состояние, не
  представлять соединяющую линию как интерполированные данные в tooltip.
- [Простое среднее дневных курсов не учитывает объём] → сохранить согласованную предметную формулу и явно закрепить
  её в контракте и тестах.
- [Воркспейс без прямых пар с RUB не даёт графика] → вернуть 200 с пустым массивом и подсказать пустым состоянием,
  не строить непрозрачный кросс-курс.
- [На одной дате могут быть очень разные курсы] → tooltip показывает дневное среднее с полной точностью `Rate`;
  внутридневные min/max находятся вне рамок.
- [Активный change меняет семантику времени] → реализацию этого change выполнять после или поверх
  `simplify-operations-and-analytics`, используя наивное локальное `occurred_at` без timezone.

## Migration Plan

Изменение аддитивное и не требует Alembic-миграции. Backend endpoint разворачивается раньше или одновременно с
frontend; старый frontend его не вызывает. При откате frontend удаляется новый режим, затем может быть удалён
неиспользуемый endpoint и связанный код. Данные не преобразуются и не теряются.

## Open Questions

Открытых вопросов для реализации нет. `avg` в интерфейсе зафиксирован как средняя цена одной единицы выбранной
валюты в RUB по отображаемым дневным точкам.
