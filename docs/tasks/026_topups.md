# 026. Пополнения: валюта воркспейса и валюта кошелька

Зависит от: 024, 025. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Пополнение — самостоятельный вид операции. Сумма всегда вводится в двух валютах: воркспейса и кошелька (из пары
ног выводится курс). Если валюты совпадают, достаточно одной ноги.

## Контекст и решения
- Пополнение остаётся доходом: категория обязана быть типа `income`.
- Набор валют ног = `{валюта воркспейса, валюта кошелька}`: две ноги при разных валютах, одна — при совпадающих.
  Сейчас набор ног сверяется с `wallet.currency_ids` (`_ensure_legs_match_wallet_currencies`); правило
  заменяется на новое. Стратегия проверки набора ног (одна/две) оформляется за протоколом, без ветвления по типу
  (AGENTS.md, принцип O).
- Курс не хранится, а выводится из ног (как в 011).
- Прежнее создание «просто дохода» одной ногой (`POST .../transactions` с категорией `income`) удаляется: доход
  теперь только через пополнение кошелька.
- Появляются редактирование и удаление пополнения (раньше `PUT` умел только плоскую одноногую операцию).
- Форма эндпоинтов (`/topups` как подресурс или отдельный ресурс `/api/workspaces/{workspace_id}/topups`) решается
  в design.md; список операций должен отдавать пополнения и расходы раздельно для двух вкладок frontend (031–033).

## Объём
- Сервис, схемы, роутер, репозиторий: создание, чтение, список, обновление, удаление пополнений.
- Валидация полноты и уникальности ног, положительности и точности сумм по `decimal_places` валюты.
- Unit-, smoke- и infrastructure-тесты (включая изоляцию воркспейсов).

## Вне рамок
Расходы (027), переводы (028), расчёт курса (029), frontend.

## Критерии готовности
- Пополнение кошелька в валюте воркспейса принимает одну ногу; в иной валюте — требует обе, иначе `400`.
- Категория расхода при пополнении отклоняется.
- QualityGate проходит.
