# 019. Проверка PWA (этап F3)

Зависит от: 003 (технически); выполняется последней, после 013–018, чтобы проверять уже наполненное приложение.
Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Закрыть отложенный в 003 пункт (9.4) — вручную подтвердить, что PWA действительно работает: установка, офлайн-
открытие оболочки, баннер обновления.

## Контекст и решения
- PWA-инфраструктура (manifest, service worker, кэш только оболочки без кэширования API) уже реализована в 003
  (`shared/pwa`, `vite-plugin-pwa`). Эта задача — не новый код, а ручная/полуавтоматическая проверка поведения в
  реальном браузере; если проверка выявит расхождение с описанным в 003 поведением — точечный фикс.
- Продакшен-PWA требует HTTPS; если он недоступен в текущем окружении, это документируется как известное
  ограничение, а проверяется то, что возможно локально (`make fe-preview`, эмуляция офлайн в DevTools).

## Объём
- `make fe-preview` + ручная проверка: установка приложения (desktop/mobile browser), открытие оболочки офлайн
  (авиарежим/блокировка сети в DevTools), появление баннера обновления при новой версии (`registerType: "prompt"`),
  отсутствие кэширования запросов к API (сетевые вкладки DevTools при офлайн-режиме).
- Фиксация результата проверки (что проверено, на каких браузерах/устройствах, что не удалось проверить и почему)
  в разделе «Статус» этого файла.
- Точечные фиксы, если проверка выявит расхождение с уже описанным в 003 поведением.

## Вне рамок
Push-уведомления; HTTPS-деплой (если недоступен сейчас — фиксируется как известное ограничение, не блокирует
закрытие задачи).

## Открытые вопросы
Нет — задача чисто верификационная, решений по архитектуре не принимает.

## Критерии готовности
- Результат ручной проверки задокументирован (что подтверждено, что нет и почему).
- Работоспособность PWA (установка, офлайн-оболочка, баннер обновления, API без кэша) подтверждена в доступном
  окружении, либо найденные расхождения исправлены.

## Статус
Выполнено. Проверка проведена полуавтоматически через расширение Claude in Chrome (в этой сессии оно оказалось
подключено, в отличие от предыдущих задач) на `http://localhost:5173` (`make fe-build` + `npm run preview`),
backend поднят локально в Docker (`moneyhelper-backend`, `moneyhelper-db`). HTTPS в текущем окружении недоступен —
проверено то, что возможно на `localhost` (браузеры трактуют `localhost` как secure context, этого достаточно для
Service Worker и `beforeinstallprompt`); это фиксируется как известное ограничение, не блокирующее задачу.

Подтверждено:
- **Service worker и manifest**: после сборки и открытия `/` регистрация активна
  (`serviceWorkerRegistrations[0].active === "activated"`, `scriptURL: /sw.js`), `manifest.webmanifest` отдаётся
  и содержит ожидаемые поля (`name`, `icons`, `display: standalone` и т.д.).
- **Кэш — только оболочка**: `caches.keys()` → один cache `workbox-precache-v2-...`, в нём 12 записей — HTML, JS,
  CSS, favicon/иконки, `manifest.webmanifest`; ни одного `/api/*` запроса. Соответствует `pwaOptions.ts`
  (`globPatterns` без раннтайм-кэширования API).
- **Офлайн-открытие оболочки**: контейнер `moneyhelper-backend` и `vite preview` были одновременно остановлены
  (`docker stop`, `pkill`), после чего повторная навигация на `http://localhost:5173/` полностью отрисовала
  приложение (в данном случае — экран `/login`, так как `GET /api/auth/me` не смог выполниться и `RequireAuth`
  корректно перенаправил неавторизованного) целиком из Service-Worker-кэша, без обращения к упавшим серверам.
  Сеть `/api/auth/me` при этом вернула ошибку (недоступность backend), а не устаревшие кэшированные данные —
  значит API действительно не кэшируется и его недоступность не маскируется.
- **Баннер обновления**: чтобы получить вторую версию сборки, версия в `frontend/package.json` была временно
  изменена на `0.1.0-pwatest` (после проверки возвращена обратно, `git diff` чист), пересобрано — хэш главного
  бандла изменился (`index-BqSUxPvW.js` → `index-Cjp59ge1.js`). На уже открытой вкладке с активной старой версией
  после перезагрузки страницы появился `Alert` «Доступна новая версия» с кнопкой «Обновить» (`registerType:
  "prompt"` работает как задумано — без авто-применения). Клик по «Обновить» применил новую версию: активный
  скрипт страницы стал `index-Cjp59ge1.js`, баннер исчез.
- **Установка**: на странице «Настройки» кнопка «Установить приложение» активна (получено событие
  `beforeinstallprompt`, `canInstall === true` — см. `installPrompt.ts`), клик вызывает `event.prompt()`. Диалог
  выбора «Установить/Отмена» — нативный UI браузера (не часть DOM страницы) и недоступен для проверки через
  расширение Claude in Chrome (оно управляет содержимым вкладки, а не chrome-нативными диалогами); фактическое
  подтверждение установки и запуск в standalone-режиме не проверены автоматически. Программно подтверждены все
  условия installability (валидный manifest, активный SW, иконки, secure context, само событие
  `beforeinstallprompt` получено) — то есть браузер счёл приложение устанавливаемым; ручная финальная проверка
  (нажать «Установить» в нативном диалоге на своём устройстве) остаётся открытой и не блокирует задачу, так как
  весь код и условия на нашей стороне корректны.

Расхождений с поведением, описанным в 003, не найдено — точечных фиксов не потребовалось. Дорожная карта (задачи
013–019) полностью закрыта.
