# 019. Проверка PWA (этап F3)

Зависит от: 003 (технически); выполняется последней, после 013–018, чтобы проверять уже наполненное приложение.
Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Закрыть отложенный в 003 пункт (9.4) — вручную подтвердить, что PWA действительно работает: установка, офлайн-
открытие оболочки, баннер обновления.

## Контекст и решения
- PWA-инфраструктура (manifest, service worker, кэш только оболочки без кэширования API) уже реализована в 003
  (`shared/pwa`, `vite-plugin-pwa`). Эта задача — не новый код, а ручная/полуавтоматическая проверка поведения в
  реальном браузере; если проверка выявит расхождение с описанным в 003 поведением — точечный фикс.
- Продакшен-PWA требует HTTPS; если он недоступен в текущем окружении, это документируется как известное
  ограничение, а проверяется то, что возможно локально (`make fe-preview`, эмуляция офлайн в DevTools).

## Объём
- `make fe-preview` + ручная проверка: установка приложения (desktop/mobile browser), открытие оболочки офлайн
  (авиарежим/блокировка сети в DevTools), появление баннера обновления при новой версии (`registerType: "prompt"`),
  отсутствие кэширования запросов к API (сетевые вкладки DevTools при офлайн-режиме).
- Фиксация результата проверки (что проверено, на каких браузерах/устройствах, что не удалось проверить и почему)
  в разделе «Статус» этого файла.
- Точечные фиксы, если проверка выявит расхождение с уже описанным в 003 поведением.

## Вне рамок
Push-уведомления; HTTPS-деплой (если недоступен сейчас — фиксируется как известное ограничение, не блокирует
закрытие задачи).

## Открытые вопросы
Нет — задача чисто верификационная, решений по архитектуре не принимает.

## Критерии готовности
- Результат ручной проверки задокументирован (что подтверждено, что нет и почему).
- Работоспособность PWA (установка, офлайн-оболочка, баннер обновления, API без кэша) подтверждена в доступном
  окружении, либо найденные расхождения исправлены.
