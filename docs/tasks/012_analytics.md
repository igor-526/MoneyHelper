# 012. Аналитика (этап 7)

Зависит от: 011. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md), раздел «Деньги и валюты».

## Цель
Пользователь смотрит доходы и расходы в разных разрезах.

## Контекст и решения
- Срезы: период, кошелёк, категория, валюта, тип (доход/расход).
- Валюта отображения выбирается GET-параметром.
- Курс всегда средний за диапазон анализа.
- Срезы оформляются через стратегии за протоколами (открытость/закрытость), без ветвления по типу.

## Объём
- Эндпоинты аналитики с фильтрами и группировкой.
- Пересчёт сумм в валюту отображения по среднему курсу диапазона.
- Изоляция по владельцу.
- Unit- и smoke-тесты.

## Вне рамок
Внешние курсы, графики и экспорт (frontend и отдельные задачи).

## Открытые вопросы
Решено: если для пары валют в диапазоне нет ни одного пополнения с обеими валютами — суммы в этой валюте
исключаются из итогов (не курс 1, не ошибка всего запроса), валюта попадает в `unconverted_currencies`;
округление — один раз над уже просуммированным итогом корзины (`ROUND_HALF_UP`), не по каждой операции;
`date_from`/`date_to` — оба обязательны (диапазон определяет не только фильтр, но и то, какие пополнения участвуют
в усреднении курса); агрегация — в сервисе на Python (двухфазный расчёт курс→конвертация плохо ложится на
декларативный SQL и не тестируется на fake-репозиториях без БД).

## Критерии готовности
- Аналитика возвращает суммы в выбранной валюте по среднему курсу за диапазон.
- Отсутствие курса обрабатывается предсказуемо и покрыто тестом.
- QualityGate проходит.

## Статус
Выполнено (изменение `analytics`, архив `2026-09-29-analytics`, финальная задача дорожной карты). Миграция не
требовалась — только read-эндпоинт `GET /api/analytics` поверх существующих таблиц `transactions`/
`transaction_legs`/`categories`. Единственный источник обменного курса в системе — ноги многовалютных пополнений
(011); курс между парой валют — простое среднее (не средневзвешенное) по пополнениям пользователя с ногами в
обеих валютах за диапазон запроса. Три оси группировки (`wallet`/`category`/`currency`) реализованы как стратегии
за протоколом `AnalyticsDimension`, выбираемые реестром `dict[str, AnalyticsDimension]` — без ветвления по типу,
как и требовал контекст задачи. Переводы (`transfers`) не участвуют в аналитике — не доход и не расход, нет
категории. Пустые корзины не подставляются нулём (в отличие от баланса 011 — здесь нет фиксированного конечного
множества для полного перечисления). Проверено полным QualityGate, включая `make test-infra` (оба новых
SQL-запроса на реальной БД, включая усреднение и изоляцию курса по владельцу).
