# 021. Средний курс кошелька

Зависит от: 011, 020. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Пользователь видит, по какому эффективному курсу (например, в RUB) фактически была совершена трата в другой
валюте многовалютного кошелька (например, в CNY), не заводя отдельно курс сделки вручную.

## Контекст и решения
- Кошелёк с несколькими валютами (008) хранит остатки всех своих валют одновременно; пополнение (011) обязательно
  указывает суммы во всех валютах кошелька разом, из чего выводится курс конкретного пополнения.
- Рассмотренная и отклонённая альтернатива — FIFO-партии (тратится сначала самое старое пополнение, у каждого
  своя порция и свой курс). Отклонена пользователем в пользу более простого варианта: **средний курс кошелька**,
  без учёта очерёдности расходования. Это не требует переделки модели баланса/трат (010) — эффективный курс
  становится производным read-only значением.
- Формула — прямой прецедент уже сданной задачи 012 (аналитика, `openspec/specs/analytics/spec.md`): курс пары
  валют = простое арифметическое среднее (не средневзвешенное) `target_leg.amount / source_leg.amount` по всем
  пополнениям с ногами в обеих валютах. Разница с 012 — выборка пополнений сужается не до всех кошельков
  воркспейса за диапазон дат, а до одного конкретного кошелька (без диапазона дат — курс кошелька за всю его
  историю пополнений, если не будет решено иначе при `/opsx:propose`).
- Воркспейсы (020) уже реализованы — кошелёк принадлежит воркспейсу, пополнения этого кошелька тоже; курс
  естественным образом не смешивается между воркспейсами, так как пополнения чужого воркспейса физически не могут
  быть пополнениями данного кошелька.

## Объём
- Расчёт среднего курса пары валют по одному кошельку, на лету, без кэша (тот же принцип, что у баланса и
  аналитики).
- Точная форма выдачи (новый эндпоинт вида `GET /api/workspaces/{workspace_id}/wallets/{wallet_id}/rates`, либо
  поле в существующем ответе балансов, либо что-то ещё) — открытый вопрос, решается в design.md при
  `/opsx:propose`.
- Валюты кошелька без единого пополнения с обеих сторон — не имеют среднего курса; поведение (исключение из
  ответа, отдельное поле вроде `unconverted_currencies` в 012) — тоже решается в design.md, по аналогии с 012.
- Unit- и smoke-тесты.

## Вне рамок
FIFO-партии/очерёдность расходования (отклонённая альтернатива); внешние источники курсов; frontend-отображение
эффективного курса — отдельная будущая задача.

## Открытые вопросы
Форма выдачи курса (новый эндпоинт vs поле существующего ответа) и нужен ли диапазон дат (курс за всю историю
кошелька vs за период, по аналогии с обязательным диапазоном в 012) — решаются в design.md.

## Критерии готовности
- Для кошелька с несколькими валютами можно получить средний курс между его валютами, выведенный из истории его
  пополнений.
- Курс не смешивается между воркспейсами и между кошельками.
- QualityGate проходит.

## Статус
Выполнено (изменение `wallet-average-rate`, архив `2026-09-30-wallet-average-rate`). Новый эндпоинт
`GET /api/workspaces/{workspace_id}/wallets/{wallet_id}/rates?target_currency_id=<uuid>` — без диапазона дат, курс
за всю историю пополнений кошелька, ровно как решено в design.md. Алгоритм усреднения (простое среднее
`target/source` по ногам пополнений с обеих сторон) вынесен из `AnalyticsService._average_rates` в чистую функцию
`core/services/rate_averaging.py::average_rates` и переиспользован обоими сервисами — `AnalyticsService` теперь
тонкая обёртка над ней, поведение аналитики не изменилось (её тесты остались зелёными без правок). Новый метод
репозитория `TransactionRepository.list_topup_legs_for_wallet_rates(workspace_id, wallet_id)` — отдельный от
`list_topup_legs_for_rates`, без диапазона дат, тот же приём сосуществования узкоспециализированных методов в одном
протоколе, что уже был в 012. Курс — новый тип схемы `Rate` (10 знаков после запятой, `PlainSerializer` в строку,
по образцу `Money`, но без привязки к `decimal_places` конкретной валюты). `WalletRateService` — отдельный сервис
(не метод `WalletService`), по образцу `BalanceService`/`AnalyticsService`; валюта кошелька без подходящих
пополнений не получает курс `1`, а перечисляется в `unrated_currency_ids`; кошелёк с одной валютой и
`target_currency_id`, не входящий в валюты кошелька, обработаны explicit (пустой результат и `ClientError`
соответственно). Единственное отклонение от design.md — файл схем ответа лёг в `api/schemas/wallet_rate.py`, а не
`core/schemas/`, как там написано по ошибке (в проекте `core/schemas/` зарезервирован под переиспользуемые типы
вроде `Money`/`Rate`, а не под ответы конкретных эндпоинтов — тот же прецедент, что `api/schemas/balance.py`).
Миграция не потребовалась (только `SELECT`). Проверено полным QualityGate: `make format`, `make lint`, `make test`
(backend 435/435, frontend 451/451 — frontend не затронут), `make test-infra` (141/141, без изменений — новых
SQL-специфичных сценариев не потребовалось).
