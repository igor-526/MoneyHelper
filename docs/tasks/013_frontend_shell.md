# 013. Каркас разделов и общие компоненты (этап F2a)

Зависит от: 003, 005. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Подготовить общую инфраструктуру для будущих экранов (кошельки, категории, операции, пополнения/переводы,
аналитика): переиспользуемые компоненты и типы, которыми они будут пользоваться. Навигацию и маршруты каждый
следующий раздел заводит сам, в своей задаче (см. «Контекст и решения»).

## Контекст и решения
- Дальнейшие frontend-задачи (014–018) декомпозированы по капабилити backend: кошельки → категории → операции →
  пополнения/переводы → аналитика (решение дорожной карты, [002_roadmap.md](002_roadmap.md)).
- **Навигация — не единый пункт этой задачи, а ответственность каждого раздела при своей реализации.** Нижняя
  панель вмещает не больше 5 пунктов (правило AGENTS.md); сейчас заняты 2 («Главная», «Настройки»). Решено:
  «Кошельки» (014), «Операции» (016) и «Аналитика» (018) добавляют свой пункт `navItems`/маршрут сами — ровно 5
  пунктов итого. «Категории» (015) — без отдельного пункта, маршрут `/categories`, вход — ссылка со страницы
  «Настройки» (управление справочником, не частое действие). «Переводы» (017) — без отдельного пункта, доступны
  из раздела «Операции» (ссылка/переключатель на том же экране, точный UI решает 017). Эта задача (013) саму
  навигацию не трогает — только готовит компоненты, которыми будущие экраны будут пользоваться.
- Иконки Lucide и их статическая карта (`shared/ui/icons.ts`, `Icon`) уже реализованы в 003 и синхронизированы с
  `backend/src/core/icons.json` тестом (`icons.sync.test.ts`) — новый реестр бизнес-иконок заводить не нужно,
  только компонент выбора одной из уже существующих (`BUSINESS_ICON_NAMES`). Иконки для будущих пунктов навигации
  (014/016/018 добавят их сами) — обычные Lucide-иконки интерфейса, идут в `UI_ICONS`, а не в `BUSINESS_ICONS`:
  `BUSINESS_ICONS` — закрытый список, сверяемый с backend `icons.json`, добавление туда произвольной
  навигационной иконки сломает `icons.sync.test.ts`.
- Валюты (`GET /api/currencies`) — маленький справочник; кешируется TanStack Query, но ответ backend всё равно
  постраничный (`Page[CurrencyOut]`) — запрос берёт заведомо большой `limit`, чтобы получить всё одним запросом.
- Пустые состояния — единый переиспользуемый компонент с иконкой/текстом/кнопкой действия, без иллюстраций (нет
  другого источника изображений в приложении, кроме Lucide-иконок) и без отдельного мастера первичной настройки
  (решение дорожной карты).
- Суммы денег на frontend — **всегда строка**, никогда не приводятся к JS `number` (та же причина, что заставила
  backend использовать `Decimal`/`NUMERIC`, а не `float`: точность). `MoneyInput` — обычный `Input` с
  контролируемым строковым значением и фильтрацией ввода по регулярному выражению, не antd `InputNumber` (тот
  приводит значение к `number` внутри, теряя точность на больших суммах/восьми знаках после запятой).
- Списки кошельков/категорий/операций/переводов (014/015/016/017) все постраничные (`Page[T]` на backend) — общий
  тип `Page<T>` на frontend заводится один раз здесь, не дублируется в каждой задаче.

## Объём
- `shared/api/Page.ts` — тип `Page<T>` (`items`, `total`, `limit`, `offset`), соответствующий `core/schemas/pagination.py`
  backend; экспорт из `shared/api`.
- `shared/ui/CurrencyPicker` — выбор одной или нескольких валют (проп `multiple?: boolean`; `Select`, данные
  `GET /api/currencies` через TanStack Query, `hook useCurrencies`).
- `shared/ui/IconPicker` — выбор иконки из `BUSINESS_ICON_NAMES` с превью через `Icon`; на телефоне — `Drawer`, на
  широком экране — `Modal` (первое в проекте применение уже сформулированного в AGENTS.md правила «Drawer вместо
  Modal на телефоне» к собственному модальному сценарию — раньше в коде ни один компонент так не разделялся).
- `shared/ui/MoneyInput` — контролируемый ввод суммы строкой: `inputMode="decimal"`, необязательный проп
  `decimalPlaces` (ограничивает число знаков, когда валюта уже выбрана), без округления на клиенте.
- `shared/ui/EmptyState` — пустое состояние: иконка + текст + опциональная кнопка действия.
- Тесты всех новых компонентов/типов.

## Вне рамок
Сами экраны кошельков/категорий/операций/пополнений-переводов/аналитики и их навигация/маршруты (014–018, каждая
задача заводит свой пункт `navItems`/маршрут сама, см. «Контекст и решения»); мастер первичной настройки; ручная
проверка PWA (019).

## Открытые вопросы
Нет — решены оркестратором при постановке (см. «Контекст и решения»): владение навигацией по задачам, `MoneyInput`
как строка не `InputNumber`, `EmptyState` без иллюстраций, `IconPicker` — `Drawer`/`Modal` по ширине экрана.

## Критерии готовности
- `CurrencyPicker`/`IconPicker`/`MoneyInput`/`EmptyState`/`Page<T>` готовы, покрыты тестами и соответствуют
  mobile-first правилам AGENTS.md (touch-цели ≥ 44 px, шрифт полей ≥ 16 px, `Drawer` на телефоне).
- Эта задача не меняет `navItems`/`routes.tsx` — их меняют 014/016/018 при добавлении своих разделов.
- QualityGate проходит.

## Статус
Выполнено (изменение `frontend-shell`, архив `2026-09-29-frontend-shell`). Каждый компонент — своя папка в
`shared/ui/` (`CurrencyPicker`, `IconPicker`, `MoneyInput`, `EmptyState`) с презентационным файлом, hook/чистой
функцией отдельно и тестами рядом, по образцу `shared/ui/toast/`; `shared/api/Page.ts` — тип `Page<T>`.
`CurrencyPicker` — один компонент с дискриминированными пропами по `multiple` (не два раздельных). `mapCurrency`
— явная чистая функция snake_case→camelCase (единственный такой случай в проекте, обоснован в design.md).
`MoneyInput` — обычный `Input` со строковым значением и `isValidMoneyAmount`, без `InputNumber` (потеря точности).
`IconPicker` — первое в проекте применение правила «`Drawer` на телефоне, `Modal` на широком экране» к
собственному модальному сценарию (прецедента в коде раньше не было, хотя правило уже было сформулировано в
AGENTS.md). `navItems`/`routes.tsx` не менялись — их заводят 014/016/018 при добавлении своих разделов. Backend
не затронут. Проверено полным QualityGate (`make format/lint/test`, backend и frontend).
