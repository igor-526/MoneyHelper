# 020. Воркспейсы (этап 8)

Зависит от: 008, 009, 010, 011, 012. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Пользователь ведёт несколько независимых рабочих пространств (например, по поездкам) в рамках одного аккаунта;
данные одного воркспейса нигде не видны и не учитываются в другом.

## Контекст и решения
- Воркспейс принадлежит одному пользователю; совместного доступа нескольких пользователей к одному воркспейсу нет
  (вне рамок — как и роли/приглашения).
- Изоляция полная — как сейчас между пользователями: кошельки, категории, операции, переводы и производные от них
  (балансы 011, аналитика 012) относятся ровно к одному воркспейсу. Категории **не** общие для пользователя —
  список категорий отдельный в каждом воркспейсе, симметрично кошелькам/операциям/переводам.
- Курс в аналитике/балансах (среднее по пополнениям) считается только по пополнениям того же воркспейса — как и
  сейчас считается только по операциям самого пользователя.
- Существующие тестовые данные (кошельки/категории/операции, использовались для проверки PWA, 019) можно не
  сохранять — реальных пользователей ещё нет, миграция вправе очистить существующие таблицы вместо переноса в
  дефолтный воркспейс.

## Объём
- Таблица `workspaces` (владелец, название), миграция.
- Все существующие сущности (`wallets`, `categories`, `transactions`/`transaction_legs`, `transfers`) становятся
  scoped по воркспейсу вместо прямой привязки к пользователю; изоляция по воркспейсу подтверждается там же, где
  сейчас подтверждается изоляция по пользователю (репозитории, `test-infra`).
- CRUD `/api/workspaces` (создание, список, переименование, удаление).
- Ревизия существующих `/api/wallets*`, `/api/categories*`, `/api/transactions*`, `/api/transfers*`,
  `/api/analytics`, `/api/wallets/{id}/balances` под новую модель изоляции (точная форма — в design.md: вложенные
  ресурсы под `/api/workspaces/{workspace_id}/...` или иной способ передачи текущего воркспейса — открытый вопрос
  задачи, решается при `/opsx:propose`).
- Unit- и smoke-тесты; `test-infra` на изоляцию между воркспейсами (аналог существующей изоляции между
  пользователями) и на удаление воркспейса (что происходит со связанными данными — `RESTRICT`/`CASCADE`, решается
  в design.md по аналогии с 008/010/011).

## Вне рамок
Общий доступ нескольких пользователей к одному воркспейсу, роли, приглашения; перенос данных между воркспейсами;
frontend (переключатель воркспейса, экран управления воркспейсами) — отдельная будущая задача после этой.

## Открытые вопросы
Как текущий воркспейс передаётся в запросах (путь `/api/workspaces/{workspace_id}/...` над существующими ресурсами,
или иной способ) — решается в design.md при `/opsx:propose`, с оглядкой на прецедент вложенного ресурса
(`GET /api/wallets/{wallet_id}/balances`, 011). Поведение удаления воркспейса со связанными данными (запрет при
непустом воркспейсе vs каскад) — решается там же, по аналогии с уже принятыми решениями по `wallets`/`categories`.

## Критерии готовности
- Данные одного воркспейса пользователя никак не видны и не учитываются (включая балансы, аналитику, средний курс)
  в другом воркспейсе того же пользователя.
- CRUD воркспейсов работает; существующие эндпоинты кошельков/категорий/операций/переводов/балансов/аналитики
  корректно scoped по воркспейсу.
- QualityGate проходит, включая `make test-infra` на изоляцию между воркспейсами.

## Статус
Выполнено (изменение `workspaces`, `openspec/changes/workspaces/`). Новая сущность `workspaces` (полный
вертикальный срез: entity/protocol/service/model/repository/schema/api/depends, по прямому образцу `wallets`, 008)
с CRUD `/api/workspaces*`; `DELETE` — физическое каскадное удаление без проверки на непустоту (осознанное отличие
от кошелька/категории, где 409 при наличии операций) — воркспейс явно задуман как единица удаления «стереть весь
этот контекст». `workspace_id` заменил `user_id` как колонку/параметр владения на `wallets`, `categories`,
`transactions`, `transfers` (и производных — `balances`, `analytics`) — чистое переименование во всех слоях, без
изменения формы методов; владение пользователем восстанавливается транзитивно через `workspaces.user_id`. Все
затронутые REST-пути переехали под `/api/workspaces/{workspace_id}/...` (включая
`/api/workspaces/{workspace_id}/wallets/{wallet_id}/balances` и `/api/workspaces/{workspace_id}/transactions/topups`)
— **BREAKING** для существующего frontend (013–018), осознанно, по решению из proposal.md: адаптация frontend —
отдельная будущая задача. Новая зависимость `depends/workspace.py::require_workspace` проверяет принадлежность
`workspace_id` из пути текущему пользователю (`NotFoundError` → 404, не 403 — тот же принцип, что и у чужого
кошелька/категории) и используется вместо `get_current_user` во всех вложенных роутерах.

Миграция `20260929_0008`: создаёт `workspaces`; `TRUNCATE wallets, categories, transactions, transfers CASCADE`
(решение пользователя — старые тестовые данные, использовавшиеся для проверки PWA 019, не переносятся в дефолтный
воркспейс, реальных пользователей ещё нет); добавляет `workspace_id NOT NULL` (FK `ON DELETE CASCADE`) и убирает
`user_id` на все четыре таблицы; пересоздаёт `UniqueConstraint` категорий на `(workspace_id, type, name)`.
Обратимость (`alembic downgrade -1` → `upgrade head`) проверена вручную.

Инфраструктурные тесты изоляции пользователей (`tests/infrastructure/test_*_repository.py`) создавали кошелёк/
категорию/операцию/перевод напрямую с `workspace_id = user.id` (после механического переименования параметра) —
это стало нарушать новый `FK wallets_workspace_id_fkey` и т. п. (запись должна ссылаться на реальную строку
`workspaces`, не `users`). Исправлено во всех четырёх файлах: добавлен `make_workspace()`, создающий пользователя
и воркспейс и возвращающий воркспейс; кроме `test_deleting_user_cascades_to_categories` (`test_category_repository.py`),
где нужны оба объекта — пользователь удаляется напрямую, воркспейс и всё в нём должны исчезнуть каскадно через
`workspaces.user_id`, что и подтверждено (двойной каскад user → workspace → categories). Новый
`tests/infrastructure/test_workspace_repository.py` — CRUD воркспейса и два целевых сценария задачи: полная
изоляция кошельков/категорий/операций/переводов между двумя воркспейсами **одного и того же** пользователя (не
только между разными пользователями — прямая проверка требования задачи) и каскадное удаление непустого
воркспейса, чистящее все вложенные таблицы одним запросом.

Отклонение от design.md: путь схем API — `api/schemas/workspace.py` (по факту существующей конвенции репозитория,
где сущностные Pydantic-схемы живут в `api/schemas/`, а не `core/schemas/wallet.py`-подобных файлов, которых для
других сущностей тоже нет), а не `core/schemas/workspace.py`, как ошибочно указано в design.md decision 4.

QualityGate пройден полностью, включая `make test-infra` (141/141: изоляция между воркспейсами и между
пользователями, каскадное удаление, обратимость миграции) и `make test` (backend 418/418, frontend 451/451,
frontend не затронут этим изменением). Roadmap 008–020 закрыт полностью; следующий логичный шаг — адаптация
frontend под новую модель воркспейсов (переключатель, экран управления, новые пути API) — отдельная будущая
задача.
