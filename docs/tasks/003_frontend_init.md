# 003. Инициализация frontend (этап F)

Зависит от: —. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Создать каркас frontend в `frontend/`: React + TypeScript, полностью CSR, готовый к подключению API и к QualityGate.

## Контекст и решения
- React, без серверного рендеринга; сборка Vite.
- UI-библиотека — Ant Design (antd 6). Приложение в основном используется на телефоне, поэтому подход mobile-first: адаптивный layout (нижняя навигация на телефоне), безопасные зоны, touch-цели ≥ 44 px, шрифт полей ≥ 16 px, без горизонтальной прокрутки от 320 px.
- Общение с backend только по HTTP; токены в cookies выставляет и читает backend, frontend шлёт запросы с `credentials: "include"` и не хранит токены в JS.
- Frontend и backend на разных origin (same-site); в dev — разные порты `localhost`.
- Iconpack — Lucide; обёртка над иконками лежит в `shared`.
- Каждое действие пользователя на frontend обязано обрабатывать любую ошибку: 400 (в том числе ошибки валидации по
  полям), 401, 403, 404, 409, 500 и сетевой сбой/таймаут. По ошибке пользователь всегда видит уведомление (toast);
  молчаливых сбоев быть не должно. Backend гарантирует, что ошибки, включая 500 и 404, приходят как JSON
  `{"detail": ...}` с CORS-заголовками (задача 004).
- SOLID по правилам раздела «Frontend» в AGENTS.md: presentational-компоненты и hooks, зависимость от интерфейса API-клиента.

## Объём
- Проект `frontend/` (Vite + React + TypeScript), структура `app` / `features` / `shared`.
- API-клиент за интерфейсом в `shared/api` (`credentials: "include"`, единая обработка ошибок и 401).
- Роутинг, провайдеры, базовый layout, страница-заглушка.
- Обёртка `Icon` над Lucide, принимающая имя иконки из БД.
- Тёмная тема (режимы «светлая / тёмная / как в системе», сохранение выбора, без мигания) и PWA (manifest, иконки, service worker с кэшем оболочки без кэширования API, установка, баннеры офлайна и обновления).
- Подключение Ant Design (`ConfigProvider`, русская локаль, тема под телефон) и адаптивный layout (`useIsMobile`, нижняя панель / верхняя навигация).
- Система уведомлений (Toast): хук `useToast` поверх antd `message`, типы (ошибка, успех, предупреждение), дедупликация, лимит и автоскрытие.
- Единая обработка ошибок API: клиент нормализует ответ и сетевые сбои в типизированную `ApiError` (статус, `detail`,
  поля валидации); глобальный обработчик показывает toast по умолчанию; хуки мутаций и запросов не дают ошибке пропасть и
  позволяют переопределить сообщение для конкретного действия; для 400 с ошибками по полям они привязываются к полям форм.
- Особые случаи: 401 → попытка refresh и повтор запроса, иначе переход на вход (после появления авторизации, 005);
  500 → общий toast «ошибка сервера»; сетевой сбой → toast «нет соединения».
- Корневой error boundary для ошибок рендеринга.
- Тесты на обработку ошибок: для каждого статуса 400/401/403/404/409/500 и сетевого сбоя показывается toast, действие не остаётся «висеть».
- Линтинг, форматирование, typecheck и unit-тесты; подключение к `make format`, `make lint`, `make test`.
- Настройка адреса backend через переменные окружения, пример `.env.example`.
- Обновление README.md и AGENTS.md по итогам выбора инструментов.

## Вне рамок
Экраны авторизации и бизнес-функций (появятся вместе с соответствующими backend-этапами); Docker-образ frontend, если не потребуется для запуска; офлайн-данные (кэш API, очередь мутаций), push-уведомления, HTTPS-деплой.

## Открытые вопросы
Решено (изменение `frontend-init`): npm; UI — Ant Design; Toast — `useToast` поверх antd `message`; тёмная тема — алгоритмы antd; PWA — `vite-plugin-pwa` (prompt-обновление, без кэша API); серверное состояние — TanStack Query; ошибки по полям — `fieldErrors` из `loc`; ESLint + Prettier + Vitest; интеграция в корневой `Makefile` (`fe-*`); Docker для frontend не нужен.

## Критерии готовности
- `frontend` запускается локально и обращается к backend `/health`.
- Любая ошибка API (400, 404, 500 и сетевой сбой) приводит к toast; это покрыто тестами.
- `make format`, `make lint`, `make test` покрывают и frontend и проходят.
- Тёмная и светлая темы переключаются и сохраняются; приложение устанавливается как PWA, оболочка открывается офлайн, запросы API не кэшируются.
- Интерфейс корректно выглядит и работает на телефоне (320–430 px) и на широком экране; правила мобильных паттернов описаны в AGENTS.md.
- Структура и правила описаны в AGENTS.md.
