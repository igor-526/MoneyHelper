# 023. Адаптация frontend (воркспейсы, курс кошелька, комментарии)

Зависит от: 013–018, 020, 021, 022. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md).

## Цель
Frontend снова работает и даёт пользователю пользоваться всем, что появилось на backend после 018: воркспейсы
(020, breaking change путей API), средний курс кошелька (021), комментарии к операциям (022).

## Контекст и решения
- Задача 020 сознательно сломала существующий frontend (013–018): все пути API переехали под
  `/api/workspaces/{workspace_id}/...`. До этой задачи frontend нерабочий против текущего backend.
- **Текущий воркспейс — не TanStack Query, а React Context**, в отличие от сессии (`useSession`, обычный запрос
  без контекста). Причина отступления от прецедента 013: почти каждый существующий data-хук (`useWallets`,
  `useCategories`, `useTransactions`, `useTransfers`, `useAnalytics`, `useWalletBalances` и т. д. — 18 файлов)
  должен синхронно знать `workspace_id`, чтобы построить путь запроса и ключ кэша; сессия читается один раз наверху
  дерева маршрутов (`RequireAuth`), а не десятками потребителей ниже.
- Выбор текущего воркспейса хранится в `localStorage` (ключ `moneyhelper.workspace`) — второе исключение из
  правила «токены/данные пользователя не хранятся в localStorage» (первое — `moneyhelper.theme`, см. AGENTS.md);
  это не данные пользователя, а предпочтение интерфейса (какой воркспейс открыт последним), как и тема.
- Новый `RequireWorkspace` — обёртка защищённых маршрутов уровнем ниже `RequireAuth`, по её же образцу
  (`isChecking` → спиннер, невалидный/отсутствующий воркспейс → экран выбора/создания, а не редирект на другой
  маршрут — воркспейсы не имеют собственного URL/страницы).
- Каждый ключ TanStack Query, зависящий от воркспейса, обязан включать `workspace_id` — иначе смена воркспейса
  покажет закэшированные данные предыдущего.
- Управление воркспейсами (список, создание, переименование, удаление, переключение) — в разделе «Настройки»,
  рядом с выходом и сменой пароля (уже устоявшееся место для действий уровня аккаунта, не сущностей).
- Курс кошелька (021) отображается только для многовалютных кошельков, рядом с уже существующей `WalletBalanceCard`
  (новый соседний компонент `WalletRateCard`, та же техника «сам владеет своим запросом»). Целевая валюта — первая
  по алфавиту код валюты кошелька (тот же порядок, что backend уже даёт в `currency_ids`, зафиксированный сценарием
  «Валюты кошелька отсортированы по коду» в спеке `wallets`) — без дополнительного UI-выбора валюты.
- Комментарий операции (022) — необязательное текстовое поле в `TransactionForm`/`TopupForm`; отображается как
  вторичный текст в элементе списка операций, если задан.

## Объём
- `WorkspaceProvider`/`useCurrentWorkspaceId` (React Context), `RequireWorkspace`, экран выбора/создания первого
  воркспейса (пустое состояние, без мастера — тот же принцип онбординга, что и у кошельков/категорий/операций).
- Управление воркспейсами в «Настройках»: список, создание, переименование, удаление, переключение текущего.
- Перенос путей всех существующих data-хуков (`wallets`, `categories`, `transactions` (+ `topups`), `transfers`,
  `analytics`, `useWalletBalances`) под `/api/workspaces/{workspace_id}/...`; добавление `workspace_id` во все их
  query-ключи.
- `WalletRateCard` — новый компонент, курс многовалютного кошелька рядом с балансом.
- Поле комментария в `TransactionForm`/`TopupForm`; отображение в списке операций.
- Обновление всех существующих тестов hooks/компонентов под новую модель (воркспейс в фикстурах, новые пути).

## Вне рамок
Совместный доступ к воркспейсу; ручной выбор целевой валюты для курса (UI); markdown/вложения в комментарии;
перенос данных между воркспейсами.

## Открытые вопросы
Нет — ключевые решения (Context vs Query, localStorage, размещение UI) приняты выше; частности верстки — по месту
при реализации, как и в 013–018.

## Критерии готовности
- Frontend полностью работает против текущего backend (все пути обновлены).
- Пользователь без воркспейсов видит пустое состояние с призывом создать первый; переключение воркспейса не
  показывает данные другого.
- Курс многовалютного кошелька виден рядом с балансом; комментарий операции можно задать, увидеть и изменить.
- QualityGate проходит.

## Статус
Выполнено (изменение `frontend-workspaces-adaptation`, архив `2026-10-01-frontend-workspaces-adaptation`). Самая
крупная frontend-задача проекта — перенос 18 существующих data-хуков (`wallets`/`categories`/`transactions`/
`transfers`/`analytics`) и их тестов под пути `/api/workspaces/{workspace_id}/...`, новая фича `workspaces`
(`WorkspaceContext`/`RequireWorkspace`/CRUD/управление в «Настройках»), `WalletRateCard` (021) и комментарий
операции (022).

Отклонения/уточнения от design.md, обнаруженные по ходу реализации:
- **Авто-выбор единственного воркспейса — derived-значение при рендере, не `useEffect` с `setState`.** Исходный
  план (эффект, персистящий автовыбор в `workspaceStorage`) нарушал правило `react-hooks/set-state-in-effect`
  (`eslint`, найдено при `make format`). Переписано: `currentWorkspace = storedWorkspace ?? (единственный воркспейс)`
  вычисляется прямо в теле компонента, без побочного эффекта и без записи в `localStorage` для этого случая —
  значение и так детерминированно выводится заново на каждом рендере, пока воркспейс остаётся единственным.
- Два наименования локальных filters-ключей (`transactionsQueryKey`/`transfersQueryKey` в `useTransactions.ts`/
  `useTransfers.ts`) конфликтовали с новыми экспортируемыми `xxxQueryKey(workspaceId)` — локальные переименованы в
  `transactionListKey`/`transferListKey` (design.md этого явно не называл, но логически того же духа, что и
  `categoryListKey`, уже описанный там).
- Маршрутные тесты (`renderApp`/`withSession`) неявно зависели от рабочего `RequireWorkspace` — `test/session.ts`
  получил `DEFAULT_WORKSPACE`/ответ на `GET /api/workspaces` по умолчанию, не упомянутый в design.md отдельно, но
  необходимый, чтобы существующие тесты оболочки не упирались в экран выбора воркспейса.

QualityGate зелёный целиком: `make format`, `make lint`, `make test` (backend 445/445 — не затронут, frontend
487/487, накопилось с 466 по ходу задачи — группы 9–11 добавили новые тесты). Полный прогон стабильно зелёный
несколько раз подряд; один раз в процессе работы (до финального прогона) встретился нестабильный счётчик
«N errors» в выводе vitest без единого реального упавшего теста и без видимого стектрейса ошибки — по характеру
совпадает с уже задокументированным ранее в памяти сессии (задача 017) флейком таймера `Drawer`/`IconPicker`
(`@rc-component/util`), не связан с кодом этой задачи и не блокирует её.

Ручная проверка в браузере (по образцу 019) не выполнена — расширение Claude in Chrome в этой сессии не было
подключено (`list_connected_browsers` вернул пустой список). Зафиксировано как известное, не блокирующее
ограничение — как и в 019, все проверяемые автоматически условия (типы, тесты, сборка) подтверждены.
