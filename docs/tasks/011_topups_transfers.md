# 011. Пополнения и переводы (этап 6)

Зависит от: 010. Дорожная карта: [002_roadmap.md](002_roadmap.md). Правила: [AGENTS.md](../../AGENTS.md), раздел «Деньги и валюты».

## Цель
Пополнение кошелька с несколькими валютами (со сбором курса) и переводы между кошельками.

## Контекст и решения
- Пополнение — это доход.
- При пополнении кошелька с несколькими валютами обязательно указываются суммы во всех его валютах; курс выводится из ног (например 10 000 RUB и 780 CNY).
- Перевод между кошельками возможен, только если у них есть хотя бы одна общая валюта.
- Варианты поведения оформляются через стратегии за протоколами, а не через ветвление по типу.

## Объём
- Валидация полноты ног при пополнении кошелька с несколькими валютами.
- Расчёт и хранение курса пополнения.
- Перевод между кошельками с проверкой общей валюты.
- Unit- и smoke-тесты.

## Вне рамок
Внешние источники курсов; аналитика (012).

## Открытые вопросы
Решено: перевод — отдельная сущность/таблица `transfers` (не пара связанных операций — иначе `category_id` у
`transactions` пришлось бы делать необязательным или вводить синтетическую категорию перевода, размывая семантику
«категория = доход/расход»); расчёт курса при частичных ногах не возникает — частичные ноги запрещены валидацией
(пополнение требует ровно полный набор валют кошелька), курс не хранится отдельным полем, а выводится из
сохранённых сумм ног; перевод с разными валютами на входе и выходе не поддерживается (Non-goal) — перевод всегда
одна валюта без конвертации, допустимая только если входит в набор валют обоих кошельков.

## Критерии готовности
- Пополнение без всех валют кошелька отклоняется; перевод без общей валюты отклоняется.
- Курс воспроизводим по сохранённым ногам.
- QualityGate проходит.

## Статус
Выполнено (изменение `transfers`, архив `2026-09-29-transfers`). `Transaction` стала ногозависимой (`legs`,
value-object `TransactionLeg`) — задел, заложенный в design.md `transactions` (010). `POST
/api/transactions/topups` создаёт пополнение с несколькими ногами (категория обязана быть `income`, набор валют
ног обязан ровно совпадать с валютами кошелька); обычные `POST`/`PUT /api/transactions` остались плоскими (одна
нога). Новая таблица `transfers` (миграция `20260929_0007`, `from_wallet_id`/`to_wallet_id`/`currency_id` — `ON
DELETE RESTRICT`, `CheckConstraint` на положительность суммы и на различие кошельков); полноценный CRUD
`/api/transfers*`. Баланс кошелька (`GET /api/wallets/{wallet_id}/balances`, переехал в `api/balances.py`) теперь
вычисляется `BalanceService`, суммирующим вклад операций и переводов через протокол-стратегию
`BalanceContributor` — расширяемо без ветвления по типу источника. Проверено полным QualityGate, включая `make
test-infra` (RESTRICT/CheckConstraint переводов, батч-агрегация ног без N+1, баланс с переводами, изоляция — все
на реальной БД).
